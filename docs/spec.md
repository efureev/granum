# Техническое задание: `@feugene/granum`

Версия документа: 2.6 · 2026-10-20 · статус: действует — granum 3.6, темы и режимы
([ADR-11](./decisions.md)). Версия 1.0 описывала granum 1.x–2.x.

Смежные документы: [`invariants.md`](./invariants.md), [`manifest.md`](./manifest.md),
[`decisions.md`](./decisions.md), [`plan.md`](./plan.md).

---

## 1. Назначение и цели

### 1.1 Проблема

Пресет v1 (`@feugene/unocss-preset-granular`) решает задачу «приложение платит только
за выбранные компоненты», но делает это внутри чужого оркестратора. Следствия:

1. Порядок слоёв, сканирование контента, safelist и виртуальные модули существуют в
   терминах UnoCSS. То, что пресет возвращает `content`, UnoCSS игнорирует, и нужен
   обходной хелпер `granularContent` в пользовательском конфиге.
2. Классы компонентов извлекаются на стороне приложения повторным сканированием
   `node_modules/**/dist`, хотя набор классов компонента известен уже при публикации.
3. Селекция компонентов управляет только CSS. JS-состав бандла определяют импорты
   приложения; одна и та же селекция не гарантирует согласованности JS и CSS.
4. Приложение обязано нести `unocss`, `presetMini`, трансформеры и знать их семантику.

### 1.2 Цели

| # | Цель | Измеримый признак |
|---|---|---|
| G1 | Собственный оркестратор конвейера | В приложении нет `uno.config.ts`; один конфиг `granum.config.ts` и один плагин в `vite.config.ts` |
| G2 | Явная точка передачи «пакет → приложение» | Провайдер публикует `granum.manifest.json`; приложение не обходит `node_modules` глобом для извлечения классов: файлы пакета оно читает, только когда отпечаток словаря разошёлся с движком приложения, и только те, что назвал манифест (E-16); провайдер объектной формы без манифеста сканируется целиком (R-6) |
| G3 | Одна резолюция — три канала (JS, CSS, токены) | Все три канала строятся из одного объекта `Resolution` за один вызов |
| G4 | Нулевые внешние зависимости у ядра | `.`, `./contract`, `./engine`, `./runtime` не имеют `dependencies`; `./build`, `./vite`, `./node` — только `vite` как peer |
| G5 | Движок утилит — сменный адаптер | Интерфейс `GranumEngine`; встроенная реализация заменяется без изменения остального кода |
| G6 | Совместимость по результату с пресетом v1 | Множество CSS-правил стенда `bench-one`, собранного granum, равно множеству правил того же стенда на пресете v1 (см. §16) |
| G7 | Диагностика без сборки приложения | `granum doctor / explain / why-css / tokens` работают по манифестам и карте движка |

### 1.3 Не-цели

- Написание движка утилит с нуля. Правила и генератор берутся форком (ADR-2).
- Замена бандлера. Минификация и tree-shaking JS остаются работой Vite/rolldown.
- Поддержка фреймворков, кроме Vue 3, на первом релизе. Контракт фреймворко-независим,
  но фикстуры и тесты — Vue.
- Совместимость по API с пресетом v1. Совместимость — по результату и по контракту
  провайдера с перечисленными изменениями (§15).
- Инспектор в браузере, IDE-плагин, автодополнение классов.

## 2. Границы

### 2.1 В объёме

- Пакет `@feugene/granum` с точками входа `.`, `./contract`, `./engine`, `./build`,
  `./vite`, `./node`, `./runtime`, `./codegen` и CLI `granum`.
- Формат манифеста провайдера и его валидация.
- Плагин сборки провайдера: раскладка, CSS, извлечение классов, скан токенов,
  эмиссия манифеста, интеграция с codegen.
- Плагин приложения: конфиг, резолюция, CSS-канал с каскадными слоями, JS-канал,
  канал токенов и тем, dev-режим с HMR, отчёт сборки.
- Движок утилит отдельным пакетом: вендоренные `@unocss/core` + `@unocss/preset-wind3`
  (тот построен на `@unocss/preset-mini`, поэтому вендорятся оба) плюс одно
  доп-правило — альфа на произвольном цвете.
- Диагностика и CLI.
- Фикстуры: три провайдера (аналоги `simple`, `extra-simple`, `heavy`), приложения-
  интеграционные тесты, стенды замера веса.
- Документация `docs/ru` и `docs/en`, руководство по миграции с пресета v1.

### 2.2 Вне объёма

- Изменения в репозитории `unocss-preset-granular`. Он остаётся как есть; granum
  разрабатывается в новом репозитории.
- Адаптеры движка для внешнего `unocss` и Tailwind. Интерфейс их допускает, реализация
  не входит в первый релиз.
- Генерация утилит на сборке провайдера («прекомпиляция»). Заложена в манифест и
  интерфейс движка, реализуется после первого релиза (ADR-1).

## 3. Термины

| Термин | Определение |
|---|---|
| **Провайдер** | npm-пакет, публикующий компоненты, их стили, токены и темы по контракту granum и несущий `granum.manifest.json` |
| **Компонент** | единица селекции: директория `components/<Name>/` в `dist` провайдера с `index.js`, описанная дескриптором |
| **Дескриптор** | объект `GranumComponentDescriptor`, объявленный автором компонента в `config.ts` |
| **Манифест** | `granum.manifest.json` — машинно-порождённое описание провайдера: компоненты, зависимости, классы, safelist, токены, темы, пути |
| **Приложение (потребитель)** | проект, который подключает провайдеров через `granum.config.ts` и плагин `granum()` |
| **Селекция** | множество компонентов, выбранных приложением, после транзитивного замыкания по зависимостям |
| **Resolution** | чистая структура данных — результат резолвера над манифестами и конфигом; единственный вход для всех каналов |
| **Канал** | одна из трёх ветвей вывода из Resolution: JS, CSS, токены и темы |
| **Движок** | реализация `GranumEngine`: набор классов → CSS и карта «класс → правило» |
| **Статические классы** | классы, извлечённые из исходников компонента при сборке провайдера |
| **Safelist** | классы компонента, которые собираются в рантайме из JS и статически не извлекаются; объявляются автором |
| **Слой** | каскадный слой CSS (`@layer`), в который попадает часть вывода |
| **Токен** | CSS custom property (`--name`), объявленная провайдером или приложением |
| **Тема** | дизайн-язык: именованный полный набор значений токенов — режимонезависимые (`root`) и по режимам — плюс метаданные. Id — slug `^[a-z][a-z0-9-]*$` (C-24). В CSS приложения ровно одна активная тема (T-6) |
| **Режим** | вариант внутри темы: значения режимозависимых токенов. Набор открытый, главный — `light`. Имя — slug без дефиса `^[a-z][a-z0-9]*$` (C-24) |
| **Пара** | значение активации на корне: `<тема>-<режим>` (`slate-light`, `ink-dim`); разбирается по последнему дефису (A-28) |
| **Каталог тем** | темы, которые объявляет провайдер; в графе приложения не больше одного владельца каталога (A-23) |
| **Реестр токенов** | словарь владельца тем: имя токена → природа `root` или `mode`; по нему проверяется полнота темы (C-30) |
| **Превью-тема** | тема, показанная рядом с активной полными блоками пар, без выхода под `:root` (A-32) |

## 4. Архитектура

### 4.1 Конвейер

Визуальная схема конвейера — [`architecture-pipeline.html`](./architecture-pipeline.html)
(откройте файл в браузере).

```
СБОРКА ПРОВАЙДЕРА (один раз, при публикации)
  исходники ──► /build ──► dist/components/<Name>/{index.js, chunks/, styles.css}
                             dist/themes/<id>.json          ← данные тем (у владельца каталога)
                             dist/granum.manifest.json      ← точка передачи

СБОРКА ПРИЛОЖЕНИЯ (vite build / dev)
  granum.config.ts ──► /core резолвер ──► Resolution ──► /vite плагин ──┬─► JS:     virtual:granum/components, guard импортов
       ▲                                                              ├─► CSS:    /engine (классы → утилиты) + сборщик @layer → virtual:granum.css
  манифесты провайдеров (через exports пакета)                        └─► токены: prune, манифест тем → virtual:granum/themes → /runtime
```

### 4.2 Точки входа пакета

| Entry | Среда | `node:`-импорты | Внешние зависимости | Содержимое |
|---|---|---|---|---|
| `.` | browser + node | MUST NOT | нет | реэкспорт `./contract` и резолвера (`resolveGranum`, типы `Resolution`, ошибки) |
| `./contract` | browser + node | MUST NOT | нет | типы контракта, `defineGranumProvider`, `defineGranumComponent`, `GRANUM_CONTRACT_VERSION` |
| `./engine` | browser + node | MUST NOT | нет | контракт `GranumEngine`, `extractClasses`, `stripComments`, `parseDialect`, `vocabularyFingerprint`; реализации движка здесь нет (INV-ENG-9) |
| `./runtime` | browser | MUST NOT | нет | `createThemeController`, `createThemeScript`, `createThemeScriptCode`, `createThemeManifest`, `createCookieStorage`, `modeFromCookie`, `themeRootAttributes`, `resolveThemeActivation` |
| `./build` | node (vite.config провайдера) | MAY | `vite` (peer) | плагин `granumProvider()` |
| `./vite` | node (vite.config приложения) | MAY | `vite` (peer) | плагин `granum()`, `defineGranumConfig` |
| `./node` | node | MAY | нет | чтение манифестов, эмиссия CSS, prune, диагностика как функции |
| `./codegen` | node (скрипты провайдера) | MAY | нет | генерация реестров, entry, `exports` |
| `./client` | — (только типы) | — | нет | амбиентные объявления виртуальных модулей (`virtual:granum.css`, срезы слоёв, `virtual:granum/themes`); кода за точкой нет |
| `bin/granum` | node | MAY | нет | CLI |

Точки входа `./build`, `./vite`, `./node`, `./codegen` **MUST NOT** быть достижимы из
браузерного кода провайдера (INV-BND-1).

### 4.3 Принципы

1. **Один источник правды на этап.** Для провайдера — дескрипторы в `config.ts` и
   исходники; для пакета — манифест; для приложения — `Resolution`.
2. **Считать один раз там, где данные родились.** Классы и потребление токенов —
   на сборке провайдера. Селекция и слои токенов — на сборке приложения.
3. **Молчаливых поломок нет.** Любое расхождение, которое пресет v1 ловил
   предупреждением или не ловил вовсе, в granum обязано быть либо ошибкой типа, либо
   ошибкой регистрации, либо строкой отчёта сборки (INV-DIAG-*).
4. **Детерминизм.** Одинаковый вход даёт побайтно одинаковый манифест и CSS
   (INV-DET-*).
5. **Границы среды — на уровне пакета.** Что можно в браузере, а что нет, задаёт
   таблица §4.2, а не дисциплина автора.

## 5. Контракт провайдера (`./contract`)

Контракт granum версии **2**. Он наследует SPEC v1 §3–§6 с изменениями §15.2; от версии 1 отличается
каталогом тем (§5.3), токенами компонентов по темам (§5.2, C-33…C-38) и подгрузкой донора по строковой
зависимости (C-4, A-31).

### 5.1 `GranumProvider`

```ts
interface GranumProvider {
  id: string                                   // npm-имя пакета
  contractVersion: 2
  components: readonly GranumComponentDescriptor[]
  theme?: GranumThemeContribution
  engine?: GranumEngineContribution            // словарь классов пакета и правила для движка
  dependencies?: readonly (GranumProvider | string)[]
  baseUrl?: string                             // только для объектной формы (тесты, локальная разработка); у манифеста база — его директория
}
```

| ID | Требование |
|---|---|
| C-1 | `id` MUST быть непустой строкой без пробелов, уникальной в графе приложения; MAY содержать `:` (разделитель ключа — последнее двоеточие, INV-SEL-1). |
| C-2 | `contractVersion` MUST быть равен `2`; `1` допустим только у провайдера без каталога тем и без токенов компонентов по темам — так читается манифест формата 2 спутника, которому смена контракта тем не нужна (M-11). Иное значение, включая большее, — `UnsupportedContractVersionError` при регистрации. |
| C-3 | Имена компонентов внутри провайдера MUST быть уникальны и являться валидными сегментами пути: `/^[A-Za-z][\w-]*$/` (INV-CON-2, `InvalidComponentNameError`). |
| C-4 | `dependencies`: объект-инстанс тянет донора в граф; строка тянет донора, если разрешается как пакет с манифестом от каталога зависимого провайдера (A-31), иначе остаётся мягким требованием присутствия по `id` (SPEC v1 §3.2). Обе формы задают порядок графа: донор раньше зависящего независимо от порядка в `providers` (INV-SEL-2), цикл через любую из них — `CircularProviderDependencyError` (INV-SEL-3). Объявление зависимости MUST NOT выбирать компоненты донора. |
| C-5 | Провайдер, ссылающийся на компоненты другого провайдера, MUST перечислить донора в `peerDependencies` (допустимы также `dependencies` и `optionalDependencies`). Сборка провайдера сверяет это с `package.json` и пишет в манифест предупреждение `peer-missing`. |
| C-6 | `baseUrl`, если задан, MUST быть абсолютным URL с завершающим `/`. Провайдер MUST NOT вычислять его литералом `new URL('..', import.meta.url)` (бандлер подменяет на `data:`), а MUST использовать `resolvePackageBaseUrl`. Для манифестной формы поле не используется. |
| C-7 | Поле `engine` MUST быть выражено в типах granum (`GranumRule`, `GranumVariant`, `GranumPreflight`), без импорта чужих пакетов. |
| C-21 | `engine` принимает форму `{ dialect?, rules?, variants?, preflights? }`. Если задано хоть одно из `rules`/`variants`/`preflights`, `dialect` MUST быть задан: правило без объявленного словаря непригодно к проверке (`InvalidProviderError('rules-without-dialect')`). Диалект, не проходящий E-1, — `InvalidProviderError('invalid-dialect')`. |
| C-22 | Провайдер MAY объявить `engine: { dialect }` без правил — как утверждение о словаре своих классов. Сборка сверяет утверждение с диалектом движка, которым её запустили; расхождение — `EngineDialectMismatchError`, а не молчаливая запись чужого диалекта в манифест (INV-ENG-10). Отпечаток провайдер не объявляет: это свойство не пакета, а реализации, собравшей его. |
| C-23 | Пакет, не использующий утилиты и не расширяющий словарь, MUST иметь право не объявлять `engine` вовсе. Диалект и отпечаток его манифеста — `null` (E-3). |

### 5.2 `GranumComponentDescriptor`

```ts
interface GranumComponentDescriptor {
  name: string
  dependencies?: readonly GranumComponentDependency[]   // 'Name' | 'providerId:Name' | { provider, components }
  safelist?: readonly string[]
  cssFiles?: readonly string[]                          // после define*: `components/<Name>/<file>`, относительно корня раскладки
  themesDir?: string                                    // токены компонента по темам: <dir>/<тема>/{root,modes/<режим>}.{json,css}
  dynamicTokens?: readonly string[]                     // токены, имена которых собираются в рантайме
  group?: string
  sourceUrl?: string                                    // `import.meta.url` модуля config.ts; нужен только сборке провайдера
}
```

| ID | Требование |
|---|---|
| C-8 | `safelist` объявляет собственные классы компонента, собираемые в рантайме. Пересечение с извлечёнными классами сборка MUST вычищать из манифеста: CSS от такой записи не зависит (класс уже в `classes`), а манифест от неё пухнет. Предупреждения на пересечении быть MUST NOT — видит ли извлечение конкретный класс, решает раскладка чанков бандлером, а не автор пакета; число вычищенных MUST печататься строкой лога сборки (INV-MAN-4). |
| C-9 | `dependencies` MUST покрывать фактические импорты: если код компонента импортирует файл из директории другого компонента (напрямую или через общий чанк), тот MUST быть достижим из `dependencies`. Проверяется сборкой провайдера по графу модулей (не по тексту бандла, как в v1), нарушение — ошибка `undeclared-dependency` (INV-CON-5). |
| C-10 | Общий код, который берут несколько компонентов, MUST лежать вне `components/<Name>/` — например в `components/shared/`; тогда он ребром графа не считается. Импорт файла ИЗ директории другого компонента ребро создаёт, даже если это константа или хелпер: на бандле хелпер от кода компонента не отличить (B-7). Объявлять такое ребро зависимостью SHOULD NOT — вместо этого общий модуль выносят, иначе компонент тянет чужой CSS и safelist. Импорт только типов (`import type`) до бандла не доживает и ребром не является. |
| C-11 | Во вводе `defineGranumComponent` `cssFiles` — пути относительно `config.ts`; хелпер нормализует их к `components/<Name>/<file>` относительно корня раскладки и сохраняет `sourceUrl`, по которому сборка провайдера находит исходник. Путь, выходящий за директорию компонента, отклоняется: `defineGranumComponent` бросает `TypeError` (id провайдера в этот момент неизвестен), `validateProvider` — `InvalidProviderError` с `reason: 'css-file-escapes-component'`. Механизма `cssFileAssetNames` нет: в манифесте лежит один путь относительно манифеста (§15.2). |
| C-12 | Ключи токенов в данных тем, файлах токенов компонентов и конфиге MUST NOT начинаться с `--`; префикс добавляет генератор. Ключ с `--` — ошибка регистрации `InvalidTokenKeyError` у провайдера (в v1 было молчаливое `----x`) и `InvalidConfigError` с путём до поля у приложения. |
| C-13 | CSS-файл токенов — файл компонента в `themesDir` (C-33) или `modes.define[*].tokensRef` приложения — читается на сборке строго: один плоский блок, другой селектор или вложенность — `TokenParseError`, а не пустой набор. Значение токена берётся целиком — со строками, `url(…)` и скобками, внутри которых бывают `;` и `{}`; повторное объявление — побеждает последнее. Файл компонента материализуется в манифест на сборке провайдера, приложению он не нужен. |
| C-14 | `dynamicTokens` — имена (или префиксы с `*`) токенов, которые компонент читает в рантайме. Они MUST попадать в манифест отдельным полем `tokens.dynamic` (а не в `tokens.consumes`: источник у них другой, и это видно в диагностике) и MUST NOT удаляться обрезкой, пока компонент в селекции. |
| C-15 | `group` включает сканирование `groups/<g>/shared/` при извлечении классов и учёт общих чанков в графе зависимостей. |
| C-33 | `themesDir` — путь относительно `config.ts`; хелпер оставляет его путём (C-20), папку читает плагин сборки провайдера и материализует в манифест `components.<Name>.tokens.themes.<тема> = { root?, modes: { <режим>: tokens } }`. Файл значений — JSON `{ "<токен без -->": "<значение>" }` или CSS с одним плоским блоком `:root {}` (C-13); селектор файла игнорируется — селекторы назначает приложение (A-28, T-9). Ключи JSON с `$` (`"$comment"`) — пояснения автора, токенами не являются. |
| C-34 | Имя подпапки MUST быть id темы, имя файла режима — имя режима (C-24); `root` — режимонезависимые токены компонента. Нарушение — `InvalidProviderError('invalid-theme-dir')` на сборке провайдера. |
| C-35 | Компонент MAY класть токены для темы чужого каталога (спутник — для темы дизайн-системы): применяются, когда эта тема активна (A-24). |
| C-36 | Подпапка темы, которой нет ни в одном каталоге графа, — предупреждение резолюции `component-theme-unknown`, а не ошибка: спутник кладёт токены для тем, о которых приложение может не знать. Предупреждение — только у компонентов селекции. |
| C-37 | Токены компонента, одинаковые для всех тем, задаются значением по умолчанию в `var(--x, …)` или файлами базовой темы, от которой наследуют остальные (C-27): отдельной «темы для всех» в контракте нет. |
| C-38 | `tokenDefinitions` и `tokenDefinitionsRef` дескриптора удалены: их место — `themesDir`. Дескриптор с ними — `InvalidProviderError('legacy-token-definitions')` с подсказкой. |

### 5.3 Темы и токены

Тема — данные, а не CSS-файл: значения токенов без селекторов. Селекторы назначает приложение из
активации режима (A-28, T-9), поэтому правила каскада едины для темы провайдера и темы приложения
([ADR-11](./decisions.md)). Именование без `--` — C-12.

```ts
interface GranumThemeContribution {
  tokensCss?: string            // тема-независимое: формулы производных и т. п. → слой tokens
  baseCss?: string              // тема-независимое базовое → слой base
  registry?: string             // JSON реестра: { "<токен без -->": "root" | "mode" }
  defaultTheme?: string         // тема, если приложение не выбрало свою (A-22)
  catalog?: Readonly<Record<string, {
    title: string
    description?: string
    docs?: string               // абсолютный URL дизайн-системы темы
    extends?: string            // родительская тема каталога
    data: string                // JSON `GranumThemeData`; extends уже разрешён (C-27)
  }>>
}

interface GranumThemeData {     // один тип для темы провайдера и темы приложения (A-22)
  id: string
  title: string
  description?: string
  docs?: string
  root: Readonly<Record<string, string>>              // режимонезависимые токены
  modes: Readonly<Record<string, GranumModeData>>
  defaultMode?: string                                // по умолчанию 'light'
  baseCss?: readonly string[]                         // @font-face и прочее режимонезависимое → слой base
  extensions?: Readonly<Record<string, unknown>>      // прозрачно для granum (C-28)
}

interface GranumModeData {
  title?: string
  colorScheme: 'light' | 'dark'
  extends?: string                                    // режим той же темы
  tokens: Readonly<Record<string, string>>            // при extends — только отличия
  fallbacks?: readonly { supports: string, tokens: Readonly<Record<string, string>> }[]
}
```

| ID | Требование |
|---|---|
| C-16 | `theme.tokensCss`, `theme.baseCss`, `theme.registry`, `catalog[*].data` — относительные пути; в манифест попадают относительно манифеста, нормализованными: без `./` и пустых сегментов (`./theme/tokens.css` → `theme/tokens.css`). Так же нормализуется `engineModule` плагина сборки. Путь абсолютный или выходящий за пакет — `InvalidProviderError` (`path-escapes-package`) при создании плагина. |
| C-24 | Id темы MUST соответствовать `/^[a-z][a-z0-9-]*$/`, имя режима — `/^[a-z][a-z0-9]*$/` (без дефиса — иначе пара `<тема>-<режим>` не разбирается однозначно); имя режима `root` запрещено. Нарушение — `InvalidProviderError('invalid-theme-id' \| 'invalid-mode-name')` при регистрации, у приложения — `InvalidConfigError` с путём до поля. |
| C-25 | `defaultMode` MUST быть ключом `modes`; не задан — `light`, и тогда `modes.light` MUST существовать (`InvalidProviderError('default-mode-missing')`). |
| C-26 | `extends` режима MUST ссылаться на режим той же темы; итоговые токены режима — цепочка предков, затем свои. Цикл — `InvalidProviderError('mode-extends-cycle')`. |
| C-27 | Наследование темы от темы (`extends` в индексе каталога) разрешает тот, кто тему собирает: провайдер — на своей сборке, приложение — до передачи объекта в конфиг. Исходник темы с `extends` MAY содержать только отличия: сборка провайдера сливает его с родителем — токены `root` и режимов по ключу, `colorScheme`/`extends`/`title` режима и `defaultMode` — свои или родителя, `fallbacks` режима и `baseCss` — свои целиком, `extensions` — слиянием верхнего уровня; метаданные (`id`, `title`, `description`, `docs`) — из записи каталога. В манифест и `dist` уходят полные данные; `data` объектной формы, которую никто не собирает, MUST быть полными. Цепочка `extends` нужна приложению только для токенов компонентов (A-24). Ссылка `extends` на тему вне каталога и цикл — `InvalidProviderError('theme-extends-unknown')` при регистрации. |
| C-28 | `extensions` granum MUST NOT интерпретировать: поле уходит в `virtual:granum/themes` как есть (T-4). Через него дизайн-система передаёт приложению, например, пропы компонентов по умолчанию. |
| C-29 | Индекс каталога в манифесте MUST содержать `title`, `extends?`, `docs?`, `data`, а также `modes` (порядок: режим по умолчанию первым) и `defaultMode`, вычисленные сборкой из данных: CLI и отчёт перечисляют темы, не читая данных. |
| C-30 | Сборка провайдера MUST проверить каждую тему каталога по реестру: каждый токен `root` есть в `root`, каждый токен `mode` — в итоговых токенах каждого режима. Нехватка — `InvalidProviderError('theme-incomplete')` с перечнем токенов. Токены компонентов (C-33) и токены, которые читаются с значением по умолчанию в `var()`, в полноту не входят. |
| C-31 | `theme.declares` MUST включать токены реестра и всех тем каталога; ключи каталога — по id (M-3). |
| C-32 | Владелец каталога MAY не иметь компонентов: провайдер только с `theme` (как C-23 разрешает не объявлять `engine`). |

## 6. Сборка провайдера (`./build`)

Плагин `granumProvider(options)` для `vite.config.ts` провайдера. Заменяет
`granularChunkFileNames`, `granularAssetFileNames`, `granularCssAssetsPlugin` и ручной
список entry из v1.

### 6.1 Раскладка

| ID | Требование |
|---|---|
| B-1 | Для каждого компонента в `dist` MUST существовать `components/<Name>/index.js`; SFC-чанки компонента MUST лежать под этой директорией (INV-LAY-1). |
| B-2 | Чанки, общие для нескольких компонентов одной группы, MUST лежать в `groups/<g>/shared/`; чанки, общие для компонентов без группы или разных групп, MUST лежать в `chunks/`. Общий чанк ребром графа не является: он входит в файлы каждого дотянувшегося компонента, а рёбра обхода находятся сквозь него (B-7, B-8) — иначе вынесенный общий хелпер превращал бы соседей в зависимости (C-10). |
| B-3 | CSS компонента (из `<style>` SFC или `cssFiles`) MUST эмитироваться в `components/<Name>/styles.css` либо по путям, объявленным в `cssFiles`. Если объявленный путь совпадает с эмитированным `styles.css`, файл в `dist` MUST содержать оба: сначала объявленный CSS, затем стили SFC — ни один не затирает другой. Двойной доставки (импорт из чанка + инлайн через манифест) MUST NOT быть (INV-CSS-5). |
| B-4 | Плагин MUST сам построить `build.lib.entry` из реестра компонентов провайдера. Точка расширения — опции плагина: `entries` (доп. точки входа: композаблы, i18n, темы) и `indexEntry` (корневой entry либо `false`). Карту `build.lib.entry` из `vite.config.ts` плагин перекрывает: Vite мержит результат хука `config` как overrides. |
| B-5 | В браузерных чанках вывода MUST NOT быть `data:text/css` на месте пути CSS-ассета (проверка на бандле, INV-LAY-3): именно в него превращается ссылка на CSS, когда база пакета вычислена литералом `new URL('..', import.meta.url)` (C-6). |

### 6.2 Извлечение

| ID | Требование |
|---|---|
| B-6 | Для каждого компонента плагин MUST извлечь статические классы из его файлов в `dist` (собственные чанки, общие чанки группы и `chunks/*`, до которых он дотягивается) экстрактором движка и оставить только токены, для которых у движка (встроенного плюс правил провайдера) есть правило. Результат — отсортированный список без дубликатов. Токены кода без правила классами не являются. |
| B-7 | Извлечение MUST выполняться по графу собранного бандла: файлы компонента — чанки, достижимые из его entry, кроме чанков чужих компонентов (любой файл директории другого компонента — ребро графа, а не файл этого). Ребро MUST считаться и по модулям чанка: бандлер кладёт в один чанк модули с одинаковым набором зависящих entry, и часть чужого компонента, импортированная общим SFC группы, лежит в `groups/<g>/shared/` — по пути файла такое ребро не видно. Файлы, не вошедшие в бандл, MUST NOT давать классов. |
| B-8 | Плагин MUST вычислить фактический граф «компонент → компонент» по импортам в бандле (чанки чужих компонентов и внешние спецификаторы `<pkg>/components/<Name>`) и сравнить с транзитивным замыканием объявленных `dependencies`; неучтённое ребро — ошибка сборки `UndeclaredDependencyError` (опция `dependencyCheck: 'warn'` понижает до предупреждения). |
| B-9 | Плагин MUST собрать потребляемые токены в `tokens.consumes`: `var(--x)` в CSS компонента, `var(--x)` и строковые литералы `'--x'` в JS его модулей. `dynamicTokens` дескриптора уезжают в `tokens.dynamic` (C-14). |
| B-10 | Плагин MUST собрать объявленные токены: из реестра, данных тем каталога, материализованных `themesDir` компонентов, `theme.tokensCss` и `theme.baseCss` (полный скан, включая блоки внутри at-rules). Файлы темы провайдер объявляет путями относительно корня раскладки (`theme/base.css`, `themes/slate.json`), а исходники лежат зеркально в каталоге `sourceDir` (по умолчанию `src`): плагин копирует их в `dist`. Данные темы с `extends` плагин дополняет из родителя (C-27) и проверяет по реестру (C-30) до записи. |
| B-11 | `@apply` в CSS компонентов (объявленные `cssFiles` и стили SFC) MUST раскрываться на сборке провайдера движком (ADR-3) только внутри плоских правил: каждый класс директивы раскрывается в ровно одно правило верхнего уровня со своим селектором, и на место директивы встают его декларации. Директива завершается `;` либо стоит последней перед `}` без неё; директива в комментарии не считается. `ApplyExpansionError`: класс без правила (`unmatched-class`); вариант — селекторный (`hover:`) или через at-rule (`md:`, `print:`, `supports-[…]:`), — и класс из нескольких правил (`container`, утилита с `@keyframes`) (`non-flat-rule`); директива вне плоского правила или с собственным блоком (`nested-context`). В `dist` директивы MUST NOT оставаться. |

### 6.3 Манифест и реестры

| ID | Требование |
|---|---|
| B-12 | Плагин MUST записать `dist/granum.manifest.json` по [`manifest.md`](./manifest.md) в хуке завершения сборки, после того как известны все чанки и ассеты. |
| B-13 | Плагин MUST убедиться, что `package.json#exports` содержит `"./granum.manifest.json"` и subpath каждого компонента; отсутствие — ошибка сборки с подсказкой запустить codegen. Опция `exportsCheck: 'error' \| 'warn' \| 'off'` понижает или снимает проверку. |
| B-14 | `./codegen` MUST генерировать: barrel, реестр провайдера (импорты конфигов и записи), `exports` компонентов и экспорт манифеста (`manifestExport`). Entry-карты нет: entry строит плагин (B-4). Поведение и ошибки — как в v1 (`GranumCodegenError`, маркерные блоки). Ноль найденных компонентов MUST NOT молча вычищать реестры: отсутствующая директория компонентов — `missing-components-dir`, а каталоги компонентов, ни один из которых не подходит под префикс, — `no-components-with-prefix`; пустая директория — законный ноль. |
| B-15 | Режим `vite build --watch` MUST перезаписывать манифест на каждую пересборку (нужно для монорепо, где приложение читает манифест соседнего пакета) — в том числе после правки `package.json`: части составных компонентов выводятся из его `exports` (B-19). |

### 6.4 Проверки на бандле

| ID | Требование |
|---|---|
| B-16 | Плагин MUST проверить, что ни один модуль сборки не импортирует `@feugene/granum/{build,vite,node,codegen}`, `node:*` или встроенные модули Node (INV-BND-1), а браузерные чанки не содержат `data:text/css` (INV-LAY-3). Проверка идёт по исходному коду модулей в `transform` (Vite подменяет `node:*` заглушкой ещё на резолве, и в выводе импорта нет) и по выводу. Нарушение — `BoundaryViolationError`; опция `boundaryCheck: 'warn'` понижает до предупреждения. |
| B-17 | Плагин SHOULD печатать сводку: число компонентов, суммарные числа классов и записей safelist, число предупреждений и путь до манифеста. Перечни остаются в манифесте — консоль их не дублирует. |
| B-18 | Плагин MUST встраивать `@feugene/granum/contract` и `@feugene/granum/runtime` в `dist` провайдера отдельным чанком `granum/contract.js` — код того granum, что собирает пакет, а не найденный в `node_modules` провайдера; остальные точки входа granum остаются внешними. Обе точки входа без зависимостей и безопасны для браузера: библиотека, создающая контроллер режимов, не тянет granum в рантайм приложения. Чанк контракта — не код компонента: классы и потребление токенов из него не извлекаются. Если `dist` после этого импортирует granum в рантайме, а `package.json` не объявляет `@feugene/granum` в `peerDependencies`, `dependencies` или `optionalDependencies`, — предупреждение `peer-missing` в манифесте. Так `dist` провайдера грузится в Node без granum: SSR с внешними пакетами и деплой с `--omit=dev` у приложения, где granum — `devDependency`. `defineGranumComponent` помечен как чистый (C-20), и неиспользуемый дескриптор бандлер приложения выбрасывает вместе с копией контракта: приложение на нескольких провайдерах не везёт их копии. |
| B-19 | Части составного компонента плагин MUST выводить из `package.json#exports`: подпуть `./components/<Part>`, чьё имя проходит правило имён и не принадлежит компоненту, а цель (любой строковый лист значения, кроме ветки `types`) — entry ровно одного компонента в `dist` или его исходный entry, записывается в `subcomponents` этого компонента в манифесте. Цели нескольких компонентов — предупреждение сборки, часть не пишется; от `exportsCheck` вывод не зависит. Импорт части провайдера-донора по её подпути MUST считаться ребром на её владельца: части донора берутся из его манифеста, свои — из своих `exports`. Пакет без манифеста (не провайдер granum) и донор, чей манифест частей не знает (собран прежней версией), оставляют ребро как есть; битый манифест донора — ошибка его чтения (INV-CON-5). |

## 7. Манифест (`granum.manifest.json`)

Полная спецификация — [`manifest.md`](./manifest.md). Здесь — требования верхнего уровня.

| ID | Требование |
|---|---|
| M-1 | Манифест MUST порождаться только сборкой; ручное редактирование запрещено и обнаруживается по хешу содержимого (INV-MAN-1). |

| M-5 | Множества `classes` и `safelist` компонента SHOULD быть дизъюнктны; пересечение записывается в `warnings` манифеста как `safelist-redundant`. |
| M-6 | Манифест MUST публиковаться через `exports["./granum.manifest.json"]`, чтобы приложение находило его через `import.meta.resolve` без вычисления `packageBaseUrl` (INV-LAY-2). |
| M-7 | Правила движка провайдера MUST ссылаться на JS-модуль по относительному пути (`engine.module`), а не встраиваться в JSON. Путь задаёт автор опцией `granumProvider({ engineModule })`; сам модуль плагин не эмитит. Провайдер, объявивший `engine`, но не передавший опцию, отгрузил бы правила в никуда — сборка пишет предупреждение `engine-module-missing` (INV-DIAG-3). |
| M-8 | Манифест MUST записывать движок, которым он порождён, блоком `engine { dialect, vocabulary, name, version?, module }`. Приложение никогда не догадывается о нём по косвенным признакам: список классов отфильтрован конкретной реализацией, и без этой записи ни доверять списку, ни объяснить пропуск нельзя (INV-MAN-9, INV-ENG-10). |
| M-9 | Писатель MUST записывать `dialect: null, vocabulary: null` тогда и только тогда, когда артефакт ни от какого словаря не зависит по факту сборки: ни одного класса, ни одной записи `safelist`, ни модуля правил. Иначе оба поля MUST быть взяты у движка сборки. |
| M-10 | Читатель MUST отклонять манифест, где `dialect` и `vocabulary` не равны `null` одновременно (`InvalidManifestError('dialect-vocabulary-mismatch')`), и манифест, где `dialect: null` при непустых `classes`/`safelist` или непустом `module` (`InvalidManifestError('dialect-without-classes')`). |
| M-11 | Читатель 3.x MUST принимать манифест формата `2` у провайдера без блока тем и без токенов компонентов по темам (`theme` пуст, `tokens.declares` компонентов пуст): спутнику смена контракта тем не нужна. Манифест формата `2` с темами — `UnsupportedManifestVersionError` с подсказкой пересобрать провайдер granum 3. |

## 8. Резолвер (`.` / `./core`)

Порт `src/core` пресета v1 с заменой входа: вместо объектов провайдеров — манифесты
(объектная форма сохраняется для тестов и локальной разработки).

| ID | Требование |
|---|---|
| R-1 | `resolveGranum(input)` MUST быть чистой функцией над `{ providers: (GranumProvider \| GranumLoadedManifest)[], components?, theme?, previews?, modes? }` без обращения к FS и сети; результат — `GranumResolution`. `GranumLoadedManifest` — `{ manifest, baseUrl }`: JSON плюс директория файла как база путей. Данные тем каталога резолверу приносит node-слой входом `themeData` (провайдер → id темы → данные) — только активной и превью (T-6), а токены `themesDir` объектной формы — входом `componentThemes`: файлов резолвер не читает. |
| R-2 | `Resolution` MUST содержать: упорядоченный список провайдеров, реестр компонентов, селекцию после транзитивного замыкания в post-order DFS (INV-SEL-2), активную тему с источником (`themeSource`), набор режимов с источником (`modesSource`), превью-темы, слои токенов и эффективные значения по режимам, объединённые множества классов и safelist по компонентам, список CSS-ссылок в порядке эмиссии, предупреждения. |
| R-3 | Резолюция MUST мемоизироваться по идентичности объекта входа, а все каналы эмиссии одного билда (CSS, виртуальные модули, guard, отчёт) MUST читать один и тот же объект `Resolution` — его держит кэш `prepareApp` в плагине (INV-RES-1). Отдельные вызовы резолвера ради одного реестра (резолвер авто-импорта A-8) допустимы: они не участвуют в эмиссии. |
| R-4 | Ошибки резолюции MUST быть типизированы и нести структурные поля (§14). |
| R-5 | Вычисление эффективного значения токена MUST выполняться одной функцией (`tokenLayers`), которую используют эмиссия CSS, отчёт, `granum tokens` и prune (T-7). |
| R-6 | Резолвер MUST принимать смешанный вход: манифесты и объекты `GranumProvider`; обе формы нормализуются в `ProviderNode`, и всё ядро ниже работает только с узлами. Для объектной формы поля `classes` и `tokens.consumes` в узле пусты, и их заполняет медленный путь в `./node`: если `baseUrl` указывает на существующий каталог раскладки, файлы компонентов под `components/<Name>/` и достижимые общие чанки сканируются экстрактором движка и `scanTokenConsumption`, объявления темы читаются по файлам, и провайдер подаётся в резолвер синтетическим манифестом — предупреждение `provider-scanned` (графа бандлера нет, рёбра не проверяются); части составных компонентов выводятся по B-19 из `exports` ближайшего вверх от раскладки `package.json`, если это пакет провайдера. Если каталога нет, поля остаются пустыми с предупреждением `provider-without-manifest`. Объектные доноры из `dependencies` подключаются наравне с перечисленными в `providers`: каждый инстанс материализуется и сканируется один раз, ссылки на него сводятся к `id`; два разных инстанса с одним `id` — `DuplicateProviderIdError`. Отброшенный `strictTokens` override — предупреждение `override-skipped` в резолюции, а не `console.warn`. |

## 9. Движок утилит (`./engine`)

Движка в ядре нет. `./engine` отдаёт контракт и хелперы; реализацию приложение
выбирает само и передаёт инстансом. Референсная реализация —
`@feugene/granum-engine-wind` (вендоренный форк UnoCSS 66.7.5 с доп-правилами);
рабочий пример движка, написанного с нуля, — `fixtures/atoms-engine`.
Обоснование — [ADR-8](./decisions.md) и [ADR-9](./decisions.md).

### 9.1 Интерфейс

```ts
interface GranumEngine {
  readonly name: string                     // реализация: для диагностики
  readonly version?: string                 // только для чтения человеком (E-5)
  readonly dialect: string                  // имя словаря: `<vendor>/<vocabulary>@<major>`
  readonly vocabulary: string               // отпечаток фактического набора имён
  extract(code: string, id: string): ReadonlySet<string>
  generate(input: EngineInput): EngineOutput | Promise<EngineOutput>
}
interface EngineInput {
  classes: ReadonlySet<string>
  theme?: EngineTheme                       // шкалы: spacing, colors, radius…; переопределяемы приложением
  rules?: readonly GranumRule[]             // правила провайдеров, добавляются ПОСЛЕ встроенных
  variants?: readonly GranumVariant[]
  preflights?: readonly GranumPreflight[]
  darkSelector?: string                     // селектор тёмных режимов для варианта `dark:` (E-20)
}
interface EngineOutput {
  css: string                               // только утилиты, без @layer
  preflight?: string                        // CSS базового уровня: `--un-*`, @property, reset (E-15)
  matched: ReadonlyMap<string, EngineMatch> // класс → { rule: string, selector: string, source: 'builtin' | providerId | 'app' }
  unmatched: readonly string[]              // классы, для которых правила нет
}
```

### 9.2 Диалект и отпечаток словаря

Это две разные величины с разными потребителями, и путать их нельзя.

**Диалект — имя словаря классов.** Формат `<vendor>/<vocabulary>@<major>`,
сравнение строгим равенством строк; мажор в конце — часть имени, а не диапазон.
Диалектом управляется ровно одно решение: грузить ли модуль правил провайдера.
Правило написано против словаря и переживает смену реализации внутри мажора.

**Отпечаток — ключ фактического множества генерируемых имён.** Им управляется
другое решение: верить ли списку классов в манифесте пакета. Внутри одного
мажора набор имён не постоянен — апстрим добавляет правила в минорах,
приложение добавляет свои правила фабрике движка, — и пакет, собранный
реализацией, знавшей меньше имён, привёз обрезанный список.

| ID | Требование |
|---|---|
| E-1 | `dialect` MUST соответствовать `/^[a-z0-9][\w.-]*\/[\w.+-]+@\d+$/`; сравнение — равенством. Примеры: `unocss/preset-mini@66`, `unocss/preset-wind3+granum@66`, `granum-fixtures/atoms@1`. |
| E-2 | Опция движка, меняющая набор генерируемых имён качественно, MUST менять диалект; опция, меняющая только вывод (префикс кастомных свойств, preflight), диалект MUST NOT менять. |
| E-3 | Диалект `null` в манифесте означает, что артефакт не зависит ни от одного словаря и ни одного не расширяет. Допустим тогда и только тогда, когда у всех компонентов пусты `classes` и `safelist`, а `engine.module` равен `null`. |
| E-4 | `vocabulary` MUST быть непустой непрозрачной строкой, сравниваемой равенством, и MUST меняться всякий раз, когда меняется множество генерируемых имён — включая правила, переданные фабрике движка. `vocabulary` равен `null` тогда и только тогда, когда `dialect` равен `null`. |
| E-5 | Ни `version` движка, ни версия его пакета MUST NOT участвовать в решениях: ни сравнением, ни диапазоном, ни вычислением подмножеств. Это поле диагностики. |
| E-6 | Ядро MUST предоставлять `vocabularyFingerprint({ rules, variants })` — детерминированный отпечаток по идентификаторам правил (строка статического, `source` и флаги динамического) и именам вариантов, независимый от порядка. Хеш некриптографический: он ключует решение сборки, подделывать его некому. Движок MAY объявить отпечаток собственной строкой, если гарантирует E-4 сам. |

### 9.3 Обязанности реализации

| ID | Требование |
|---|---|
| E-7 | Ядро MUST NOT содержать реализации движка: ни вендоренного кода, ни правил, ни пресетов. `./engine` отдаёт типы, `extractClasses`, `stripComments`, `parseDialect` и `vocabularyFingerprint` (INV-ENG-9). |
| E-8 | Движок MUST быть чистым: без FS, без сети, без глобального состояния между вызовами; повторный вызов с тем же входом даёт побайтно тот же `css` (INV-DET-2). |
| E-9 | `unmatched` MUST перечислять каждый класс без правила; молчаливое отбрасывание запрещено (INV-DIAG-2). |
| E-10 | Порядок правил: встроенные, затем провайдеров в порядке графа, затем приложения; при совпадении матчится последнее, что позволяет провайдеру переопределить встроенное (INV-ENG-3). |
| E-11 | Правила приложения передаются фабрике его движка, а не конфигу granum: у конфига поля для правил нет. |
| E-12 | Экстрактор движка MUST понимать словарь, который движок объявляет, и MUST NOT извлекать классы из комментариев SFC. Границы среза комментариев (хелпер `stripComments` ядра): в JS/TS — блочные комментарии вне строк, шаблонных строк и регэксп-литералов; в CSS — блочные вне строк и `url(…)`; в `.vue`/`.html`/`.svelte`/`.astro` — HTML-комментарии и `{/* … */}` в разметке, а тела `<script>`/`<style>` (и frontmatter `.astro`) по правилам JS и CSS; строчные — только строки, начинающиеся с двух слешей; вызовы `createCommentVNode("…")` в скомпилированных шаблонах Vue. `/*` внутри строки или в тексте разметки (`accept="image/*"`) комментария не открывает (INV-ENG-5, INV-DIAG-2). |
| E-13 | Движок MUST NOT знать о слоях, манифестах и Vite; всё это — забота сборщика CSS (§10.3). |
| E-14 | Реализация, вендорящая чужой код, MUST держать golden-тест: для фиксированного набора классов CSS сравнивается с выводом апстрима, зафиксированным в снапшоте (INV-ENG-4), и уведомление об авторстве — в `THIRD_PARTY_NOTICES.md` (ADR-2). |
| E-20 | `darkSelector` вычисляет приложение из активации и режимов активной темы с `colorScheme: 'dark'`: `[data-theme="slate-dark"], [data-theme="slate-ocean"]`. Движок, у которого есть вариант тёмного режима, MUST строить его по этому селектору, а без поля — по своему умолчанию. |
| E-21 | Селектор MUST приходить **входом** `generate`, а не опцией фабрики движка: опция меняет отпечаток словаря (E-6), и приложение пересчитывало бы классы всех манифестов. Отпечаток от `darkSelector` MUST NOT зависеть. |
| E-22 | Вариант тёмного режима — потомковый селектор: светлый остров внутри тёмной страницы его тоже совпадает. Для островов служат токены режима (T-9), а не вариант; это записывается в документации движка. |
| E-15 | CSS базового уровня — инициализацию кастомных свойств, регистрации `@property`, reset — движок MUST отдавать полем `preflight`, а не смешивать с утилитами в `css`. Это утверждение о роде CSS, не о слое: имён слоёв движок по-прежнему не знает (E-13), место в каскаде выбирает сборщик (§10.3, INV-CSS-8). Движок без preflight поле не заполняет. |

### 9.4 Сверка на стороне приложения

| ID | Требование |
|---|---|
| E-15 | Для каждого провайдера приложение MUST сравнить `manifest.engine.dialect` и `manifest.engine.vocabulary` со своим движком и действовать по таблице ниже. Решение MUST приниматься до генерации CSS. |
| E-16 | При различии отпечатков классы каждого компонента MUST быть извлечены заново из его `files` движком приложения и сравнены со списком манифеста. Пересчёт идёт с правилами провайдера, если они загружены, и без них иначе. |
| E-17 | `safelist` пересчёту MUST NOT подлежать: это авторское объявление, а не производная. |
| E-18 | Модуль правил провайдера MUST загружаться при равенстве **диалектов**, независимо от отпечатков. При различии диалектов — предупреждение `engine-rules-skipped`. |
| E-19 | Класс, который был в манифесте и потерялся при пересчёте, MUST быть подан движку вместе с остальными: он обязан остаться виден в `unmatched`. Пересчёт не имеет права делать потерю тише, чем она была (INV-DIAG-2). |

| Диалект манифеста | Отпечаток | Что делает granum | Что видит разработчик |
|---|---|---|---|
| `null` | `null` | быстрый путь, пересчёта нет | ничего: пакет ни от какого словаря не зависит |
| равен | равен | быстрый путь, классы из манифеста, правила загружены | ничего, это норма |
| равен | другой | пересчёт с правилами провайдера | при разнице наборов — `provider-classes-recovered` / `provider-classes-dropped` с числами и списками |
| другой | — | пересчёт без правил провайдера | `provider-dialect-mismatch`; плюс `engine-rules-skipped`, если пакет привёз `module` |

## 10. Плагин приложения (`./vite`)

### 10.1 Конфигурация

```ts
// granum.config.ts
export default defineGranumConfig({
  providers: ['@feugene/heavy-package', localProviderObject],   // имя пакета → манифест через exports; объект → медленный путь
  components: 'all' | ComponentSelectionItem[] | 'imports',
  theme: 'slate' | 'providerId:slate' | GranumThemeData & { sources?: string[] },   // активная тема (A-22)
  previews: ['clay'],                                           // темы для показа рядом с активной (A-32)
  modes: { names?, define?, activation?, tokenOverrides?, strictTokens?, system? },
  engine: GranumEngine,                                         // обязателен и только инстансом: windEngine() или свой
  css: { layers: true, layerPrefix: 'granum' },
  appSources: { dirs: ['./src'], extensions?: string[] },
  pruneTokens: { mode: 'off' | 'report' | 'on', keep?: (string | RegExp)[] },
  js: { guard: 'error' | 'warn' | 'off', dts?: string },
  report: { file: 'granum-report.json' | false },
})
```

| ID | Требование |
|---|---|
| A-1 | Конфиг MUST загружаться один раз на процесс Vite и валидироваться типами и рантайм-проверкой формы; ошибки формы — `InvalidConfigError` с путём до поля. Неизвестный ключ на любом уровне — тоже ошибка формы с подсказкой: куда делся ключ пресета v1 или удалённая опция, иначе ближайший допустимый ключ. Не проверяются поля инстанса `engine`, объекты в `providers` (их проверяет резолвер) и ключи токенов в `modes.tokenOverrides.<режим>` и `modes.define.<режим>.tokens` — кроме запрета `--` (C-12). `defineGranumConfig` MUST ловить лишний ключ литерала типами. |
| A-2 | `providers` в строковой форме MUST резолвиться в манифест через `import.meta.resolve('<pkg>/granum.manifest.json')` относительно корня приложения; отсутствие экспорта — ошибка `ManifestNotFoundError` с указанием пакета и подсказкой про codegen. |
| A-3 | `components: 'imports'` MUST вычислять начальную селекцию статическим сканом исходников приложения на импорты вида `<providerId>/components/<Name>` (и виртуального модуля), затем — обычное замыкание. В селекцию идёт импорт, чей провайдер есть в графе и объявляет компонент; подпуть части составного компонента (`subcomponents` манифеста) даёт её владельца; прочие пути вида `…/components/…` (алиас приложения, чужой пакет) и закомментированные импорты селекцию не меняют и ошибкой не являются. Режим SHOULD стать рекомендуемым после стабилизации (ADR-6). |
| A-4 | Плагин MUST работать без `unocss` в `node_modules` приложения. |
| A-22 | Активная тема: `theme` приложения — строка (id каталога; `providerId:id` — квалифицированная форма, разбор по последнему `:`, как C-1) или объект `GranumThemeData` (тема приложения) → иначе `defaultTheme` владельца каталога. Ровно одна. Неизвестный id — `ThemeResolutionError('unknown-theme')` со списком доступных. Источник — `themeSource: 'app' \| 'provider' \| 'default'` в резолюции и отчёте. Тема-объект MAY нести `extends` — id темы каталога, чья цепочка даёт токены компонентов (A-24); данные он не дополняет — они обязаны быть полными. `sources` — A-33. Без `theme` у владельца без `defaultTheme` активна единственная тема каталога; если тем несколько — `ThemeResolutionError('unknown-theme')`. |
| A-23 | Владельцев каталога в графе 0 или 1; больше — `ThemeResolutionError('multiple-theme-owners')` (ограничение 3.0, снимается отдельным ADR). Без владельца и без объекта темы тем нет: слой `themes` пуст. |
| A-24 | Токены компонента для активной темы T и режима M ищутся по каждому токену: внешний цикл — последовательность режимов [M, предки M по `extends`, режим по умолчанию темы], внутренний — цепочка тем [T, предки T по `extends` каталога]; берётся первое найденное значение. Так `ink-dark` без файла `ink/modes/dark` получает значение `paper/modes/dark`, а не `ink/modes/light`. Режимонезависимые токены — первое значение по цепочке тем. Режимы `define` токены компонентов наследуют от своей базы. |
| A-25 | Набор режимов: `modes.names` (включая `[]`) → иначе режим по умолчанию темы плюс ключи `modes.define`: тема собирается под приложение, и каждый следующий режим темы — решение приложения, а не умолчание. Режим, на который ссылается `extends`, в набор входить не обязан: его значения берутся по цепочке, блока у него нет. Имя, которого нет ни в теме, ни в `define`, — `ThemeResolutionError('unknown-mode')`. Источник — `modesSource: 'explicit' \| 'theme'`. |
| A-26 | `modes.define.<имя>` — режим приложения поверх режимов темы: `{ extends, tokens?, tokensRef?, title?, colorScheme? }`; `extends` — режим темы или другой `define`. Неизвестная база, неполное наследование и цикл — предупреждения `mode-extends-unresolved`, `mode-extends-partial`, `mode-extends-cycle`. Это прежние `themes.define` с `extends`, перенесённые на уровень режима. Имя `define`, совпавшее с режимом темы, даёт ту же пару — `ThemeResolutionError('activation-collision')`. Режим с неизвестной базой или в цикле наследует режим по умолчанию. `fallbacks?: [{ supports, tokens }]` — фолбэки `@supports` режима: ставятся после унаследованных от базы и перекрывают их по токену; без них режим берёт фолбэки базы, посчитанные от её значений. |
| A-27 | Тема-объект приложения MAY нести токены компонентов прямо в `root`/`modes[*].tokens`: это обычные токены, и порядок слоёв (T-7) ставит их после токенов компонентов из манифеста — тема приложения может перекрасить компонент провайдера. |
| A-28 | Активация режима — атрибут на корне: `modes.activation = { attribute = 'data-theme', value = '{theme}-{mode}' }`. Шаблон MUST содержать `{mode}`; значения всех пар активной темы, `define` и превью-тем MUST быть различны — иначе `ThemeResolutionError('activation-collision')`. Пара по умолчанию разбирается по последнему дефису: имя режима дефиса не содержит (C-24). |
| A-29 | `modes.tokenOverrides.root` ложится в `root` темы, `modes.tokenOverrides.<режим>` — в режим. `strictTokens` отбрасывает override токена, которого нет ни в данных темы, ни в токенах компонентов (`override-skipped`). Ключ `modes.tokenOverrides`, который не `root` и не режим набора, — `ThemeResolutionError('unknown-mode')`: значение, которое не попадёт ни в один блок, молча не теряется. |
| A-30 | Ключи `themes.*` granum 2 — `InvalidConfigError` с подсказкой: `themes.names` → `modes.names`, `themes.define` → `modes.define`, `themes.tokenOverrides` → `modes.tokenOverrides`, `themes.strictTokens` → `modes.strictTokens`. |
| A-31 | Строковая зависимость манифеста, которой нет в `providers` приложения, MUST загружаться в граф, если разрешается как пакет с манифестом **от каталога зависимого провайдера** (от корня приложения транзитивный пакет при строгой раскладке `node_modules` не виден). Загрузка донора MUST NOT выбирать его компоненты (C-4). Не разрешилась — прежнее мягкое требование (`UnresolvedProviderDependencyError`, если провайдера с таким id нет); если её не нашёл провайдер с токенами компонентов по темам, а владельца каталога в графе нет вовсе, — `ThemeResolutionError('theme-owner-missing')` с именем зависимости: тема его компонентов без владельца не соберётся. Компоненты подгруженного донора селекция `'all'` не выбирает. |
| A-32 | `previews` — темы, которые показываются рядом с активной (дизайн-система, портал). Для каждой — блок на каждую пару под `[<attr>="<пара>"]` с **полным** набором: `root`, режим, токены компонентов селекции, фолбэки; под `:root` превью-тема не выходит никогда. Формулы `root` со ссылкой `var(` повторяются под `[<attr>^="<тема>-"]`. Превью-темы обрезаются той же обрезкой (T-14). Это единственное исключение из T-6 и задел на рантайм-переключение тем. |
| A-4a | `engine` MUST быть обязательным полем конфига и принимать **инстанс** `GranumEngine`. Строка `'builtin'` и объект опций не принимаются: выбор реализации и её настройка — дело приложения. Отсутствие движка, объект без `dialect`/`vocabulary` или диалект, не проходящий E-1, — `InvalidConfigError` с путём до поля. |

### 10.2 JS-канал

| ID | Требование |
|---|---|
| A-5 | Виртуальный модуль `virtual:granum/components` MUST реэкспортировать именованно каждый компонент селекции из его subpath (`export { XhPanel } from '@feugene/heavy-package/components/XhPanel'`), а части выбранного составного компонента — из их подпутей (B-19); модуль MUST NOT иметь побочных эффектов, чтобы tree-shaking работал (INV-JS-1). Плагин MUST назвать каждое предупреждением с subpath для прямого импорта. При `js.dts` плагин MUST писать рядом объявления той же формы и только при их изменении: имена зависят от селекции и амбиентно невыразимы. |
| A-6 | Guard: при `js.guard !== 'off'` плагин MUST в `resolveId` распознавать импорты, попадающие в `components/<Name>/` любого провайдера графа, и для `Name` вне селекции выдавать ошибку (`error`) или предупреждение (`warn`) `component-outside-selection` с указанием импортёра (INV-JS-2). Подпуть части составного компонента ведёт в модуль владельца и MUST судиться как владелец: ошибка называет владельца и часть (`part`). Импорт компонента из корня пакета-провайдера — именованный или реэкспорт — и импорт корня целиком (`import * as`, `export * from`, `import()`) при `js.guard !== 'off'` MUST давать ошибку (`error`) или предупреждение (`warn`) `component-root-import` с импортёром и подпутём, из которого компонент берут; часть составного компонента из корня — так же, как компонент; прочие имена корня, импорт по умолчанию и одних типов допустимы. Проверяется исходный код модуля приложения, у разметки — блоки `<script>` и frontmatter. |
| A-7 | Плагин MUST NOT переписывать код провайдера и MUST NOT влиять на раскладку чанков приложения; это остаётся за бандлером. |
| A-8 | Плагин SHOULD экспортировать резолвер для auto-import инструментов (`unplugin-vue-components`-совместимый), возвращающий subpath компонента по имени (`granumResolver`), а для части составного компонента — её собственный подпуть (B-19), который guard и селекция сводят к владельцу; неоднозначность резолвер решает по тому же правилу имён, что скан тегов ниже. В режиме `'imports'` селекция пополняется сканом PascalCase-тегов в `appSources` (имя, которое объявляет ровно один провайдер графа; компонент первичен — к частям составных компонентов имя идёт, только если компонента с таким именем нет ни у кого, и часть даёт владельца), а не записями резолвера: порядок трансформаций бандлера не определён. Опция `providers` резолвера скан тегов не сужает: имя, объявленное двумя провайдерами, тегом в селекцию не попадает, даже если резолвер его подставил; такой компонент приложение импортирует подпутём явно или перечисляет в `components`. |

| A-11 | Вход движка MUST быть объединением: статических классов компонентов селекции из манифестов, их safelist, классов, извлечённых из исходников приложения (`appSources`). Классы приложения извлекаются тем же экстрактором (INV-CSS-3). Если `appSources` не задан, разметка приложения не сканируется, и плагин MUST сказать об этом строкой сборки и предупреждением `app-sources-unset` в отчёте; `appSources: { dirs: [] }` — явный отказ без предупреждения. |
| A-12 | Модули `virtual:granum/layers/<layer>.css` MUST отдавать один слой **в его обёртке `@layer`** — иначе срез отдавал бы нелейерный CSS, то есть ровно наоборот тому, что обещает слой. Объявление порядка несёт срез первого непустого слоя, поэтому конкатенация срезов в порядке слоёв MUST быть побайтно равна `virtual:granum.css` (INV-CSS-4). Пустой слой MUST давать пустой модуль. |
| A-13 | CSS компонентов MUST проходить в вывод побайтно, кроме обрезки токенов при `pruneTokens.mode: 'on'` (INV-CSS-5). `@apply` раскрывает только сборка провайдера (B-11, ADR-3): приложение директивы не раскрывает, остаток ловит `doctor` (`apply-not-expanded`). |
| A-14 | При `css.layers: false` плагин MUST эмитировать тот же порядок без обёрток `@layer` (плоский режим для приложений с нелейерным CSS). |
| A-15 | Классы приложения и провайдеров дедуплицируются: одно правило эмитируется один раз независимо от числа источников. |

Опция MUST действовать только на сборке приложения: серверная сборка HTML не порождает, а в dev хешированных ассетов нет вовсе, и CSS там приходит одним модулем. Без `build.cssCodeSplit` Vite склеивает весь CSS в один файл — плагин MUST сказать об этом предупреждением и не делить слои. |

### 10.4 Канал токенов, тем и режимов

`<attr>` ниже — атрибут активации (A-28), `<пара>` — его значение для режима.

| ID | Требование |
|---|---|
| T-1 | Значение режима в `modes.define` и `modes.tokenOverrides` — объект, ключ токена в нём — без `--`; иначе `InvalidConfigError` с путём до поля. |
| T-2 | `pruneTokens.mode: 'on'` MUST удалять из слоёв `tokens` и `themes` объявления токенов, недостижимых от корней потребления; корни: потребление в CSS компонентов селекции, в выводе движка (утилиты и preflight — правило держит токен телом декларации, а не именем класса), `tokens.consumes` и `dynamicTokens` манифестов, потребление в исходниках приложения, `keep`, плюс корни T-14. Достижимость считается по графу «токен → токены в его значении» (как в измерителе v1). |
| T-3 | `mode: 'off'` MUST NOT менять эмиссию ни на байт и не читать лишних файлов; `mode: 'report'` считает план и пишет его в отчёт, эмиссия прежняя (INV-TOK-1). |
| T-4 | Виртуальный модуль `virtual:granum/themes` MUST отдавать манифест активной темы для `./runtime`: `theme { id, title }`, `modes [{ name, title?, colorScheme, value }]` в порядке T-9, `defaultMode`, `activation { attribute, value }` (`value` — шаблон пары), `previews [{ theme { id, title }, modes [...], extensions? }]` при наличии превью (A-32), `extensions` (C-28). Он MUST NOT зависеть от селекции компонентов. |
| T-5 | Токен, который компонент требует извне и который не объявлен ни одним слоем ни в одном режиме активной темы, MUST попадать в отчёт как `token-undefined` (INV-DIAG-3). «Требует извне» — это `tokens.requires` манифеста: потребление, у которого нет ни собственного значения, ни объявления компонента о себе. Из требований MUST вычитаться три случая, и каждый — объявление, а не недосмотр: **fallback** (`var(--x, 1px)` — значение записано в самом `var()`); **присваивание самим компонентом** (`--x:` в его CSS, ключом инлайн-стиля, утилитой `[--x:1px]` или переменной `v-bind()` из `<style>`, которую Vue выставляет через `useCssVars`); **`dynamicTokens`** (имя собирается в рантайме, компонент объявил это сам). Считается множество на сборке пакета, диагностика читает готовое: иначе одно объявление значило бы в обрезке и в диагностике разное. |
| T-6 | В CSS приложения ровно одна активная тема на `:root`. Данные других тем каталога MUST NOT читаться, кроме перечисленных в `previews` (A-32). |
| T-7 | Значение токена под режимом собирается из слоёв, каждый следующий перекрывает: (1) данные темы — `root`, затем цепочка режима; (2) токены компонентов для активной темы в порядке селекции (A-24); (3) токены темы-объекта приложения (A-27); (4) `modes.define`; (5) `modes.tokenOverrides`. Одна функция считает значение для CSS, отчёта и CLI (R-5, INV-RES-3). |
| T-8 | Литерал `root` — слой `tokens` под `:root`. Значение `root` со ссылкой `var(` — под общей границей `:root, [<attr>]`: иначе формула вычислится на `:root`, и остров получит значение, посчитанное по ролям корня. |
| T-9 | Слой `themes`: режим по умолчанию — первым, под `:root, [<attr>="<пара>"]`; остальные режимы — в порядке набора (A-25), каждый под `[<attr>="<пара>"]`; затем фолбэки `@supports` в том же порядке. Порядок обязателен: `:root` совпадает с `<html>` всегда, и при равной специфичности решает позиция. Поэтому фолбэк режима по умолчанию MUST выходить под `:root:not([<attr>]), [<attr>="<пара>"]`, а не под `:root`: он стоит после всех режимов и в браузере, которому нужен, перебил бы позицией пару другого режима на корне. |
| T-10 | Токен, объявленный хоть в одном режиме темы (данными или токенами компонента), MUST получить значение в **каждом** режиме — по цепочке `extends` режима, иначе из режима по умолчанию. Значение со ссылкой `var(`, одинаковое во всех режимах, выводится один раз под общей границей `:root, [<attr>]`, а не в блоках режимов. Иначе остров режима, где токен не объявлен, унаследует значение, вычисленное по ролям родителя. Значение из режима по умолчанию — запасное: значение, которое режиму дал другой слой (токены компонента под темой-объектом приложения), им не перекрывается. Взятое из режима по умолчанию значение MUST приходить с фолбэками `@supports` режима по умолчанию для этого токена — раньше фолбэков самого режима, которые их перекрывают: иначе в браузере без фичи режим останется со значением, которого тот не понимает. |
| T-11 | Классы `.light`/`.dark` не выводятся: активация — только A-28. |
| T-12 | `colorScheme` режима выводится объявлением `color-scheme` в его блоке. |
| T-13 | `modes.system: 'media'` добавляет блок `@media (prefers-color-scheme: dark) { :root:not([<attr>]) { … } }` с первым режимом `colorScheme: dark`, а внутри того же медиазапроса — его фолбэки `@supports` под тем же селектором: под парой они корень без атрибута не достают, а блок схемы перебивает фолбэк режима по умолчанию. По умолчанию `'none'`. |
| T-14 | Данные темы и токены компонентов из манифеста — пакетный слой: обрезаются по достижимости. Корнями остаются `modes.define`, `modes.tokenOverrides`, токены темы-объекта приложения и `keep`. |
| T-15 | Токен, сохранённый обрезкой в одном режиме, сохраняется во всех режимах темы. |
| T-16 | `emitThemeStylesheet({ providers, theme?, previews?, modes?, root, css? })` в `./node` MUST отдавать CSS темы без приложения и без движка: слои `tokens`, `base` и `themes` по T-8…T-13 и A-32 с токенами всех компонентов провайдеров (кроме доноров, подгруженных по зависимости). Объектные провайдеры не сканируются: токены `themesDir` читаются по `sourceUrl`, `tokensRef` режимов приложения — от `root`. Так дизайн-система собирает `themes/<id>.css` для подключения без granum, не подделывая манифест. Те же блоки MUST отдаваться и по частям (`parts`): `root` — слой `tokens` и общий блок слоя `themes`; `modes.<режим>` — блок пары, его фолбэки `@supports` и медиазапрос системной схемы; `previews.<тема>` — пары превью. Каждый блок слоёв — ровно в одной части; `:root` — только у части режима по умолчанию; порядок слоя `themes` от раскладки не меняется. Так тема раздаётся файлом на режим, а приложение подключает `root` и свои режимы. |
| T-17 | Манифест режимов MUST быть доступен до сборки — интеграциям хоста, которые вставляют скрипт режима (RT-3) на этапе своей конфигурации, раньше Vite: `resolveThemeManifest({ providers, theme?, previews?, modes?, root })` в `./node` и `api.themeManifest(root?)` у плагина приложения (`root` по умолчанию — корень Vite, до разрешения его конфига — текущий каталог). Результат MUST совпадать с `virtual:granum/themes` (T-4) того же конфига; приложение не сканируется, движок не нужен. |

### 10.5 Dev-режим

| ID | Требование |
|---|---|
| A-16 | Виртуальные модули MUST поддерживать HMR: изменение исходника приложения перегенерирует только слой `utilities` (и `themes`/`tokens` при `pruneTokens: 'on'`); модуль, чей код не изменился, MUST NOT перезагружаться — модуль тем это JS без границы HMR, и его перезагрузка перезагрузила бы страницу. Изменение манифеста или CSS провайдера (monorepo, `--watch`) инвалидирует резолюцию целиком; за этими файлами dev-сервер MUST следить явно — пакет-воркспейс лежит вне корня приложения, а симлинк в `node_modules` watcher Vite игнорирует. В `vite build --watch` каждая пересборка после изменения файла MUST заново считать резолюцию, CSS и отчёт. |
| A-33 | Тема-объект приложения MAY перечислить `sources` — файлы, из которых она собрана. Конфиг загружается один раз на процесс Vite (A-1), поэтому изменение любого из `sources` в dev MUST перезагружать конфиг и резолюцию целиком. |
| A-34 | `css.previews: 'separate'` MUST убирать блоки тем превью (A-32) из слоя `themes` общего листа и отдавать их модулями `virtual:granum/previews.css` (все темы превью) и `virtual:granum/previews/<id>.css` (одна) — в обёртке `@layer <prefix>.themes` и с объявлением порядка слоёв, чтобы лист превью, подключённый раньше общего, не менял каскад. Порядок блоков внутри модуля — тот же, что в общем листе при `'inline'`. Тема не из `previews` MUST быть ошибкой с перечнем превью. При `'inline'` (по умолчанию) модули превью MUST быть пустыми: блоки уже в общем листе. Так превью платит только страница, которая его показывает. |
| A-17 | Извлечение классов выполняется на сборке провайдера, приложение читает готовые списки из манифестов. В пределах процесса манифесты кэшируются по пути и stat файла (`readManifestCached`), а вывод движка — по генератору и множеству классов: правка исходников приложения в dev не перечитывает манифесты и не пересобирает утилиты для того же входа. Кэш на диске не вводится: холодная подготовка `bench-one` — 3 мс, эмиссия — 25 мс. |
| A-18 | Ошибки резолюции в dev MUST показываться оверлеем Vite и в терминале с типом и полями ошибки. |

### 10.6 Отчёт сборки

| ID | Требование |
|---|---|
| A-19 | При `report.file` плагин MUST записывать в `outDir` JSON-отчёт: селекция и её цепочки, активная тема, режимы, превью-темы и их источники (`themes { theme, themeSource, modes, modesSource, previews }`), классы без правила (`unmatched`) по источникам, safelist-записи, покрытые статикой, план обрезки токенов, `token-undefined` (тот же вердикт и та же функция, что у `doctor`: только требования выбранных компонентов, T-5, INV-DIAG-4), размеры слоёв (raw/gzip/brotli) по блокам `@layer` собранного CSS после минификации (`sizesSource: 'bundle'`; при `css.layers: false` или без бандла — по эмиссии, `'emission'`) и размеры эмиссии `emissionSizes`, предупреждения. Класс из атрибута класса разметки приложения (`class`, `className`, строковые литералы `:class`), которого нет ни у движка, ни в CSS собранного бандла, ни в `.css`-файлах `appSources` (кроме CSS-модулей `*.module.css`: их классы хешируются, и литерал в разметке с ними не совпадёт), MUST попадать в `unmatched` с файлом-источником; прочие слова исходников приложения не судятся. Лист, подключённый строкой (`?raw`, `?inline`), ассетом бандла не становится — его правила видны через `.css` из `appSources`; класс из листа, который никто не импортирует, тоже не находка. В JS/TS-модулях, телах `<script>` разметки и frontmatter Astro разметкой MUST считаться только строковые литералы и статический текст шаблонных строк: регэксп-литерал и код атрибутом не являются, значение атрибута не выходит за границу литерала. В JSX разметка — сам код, и атрибут ищется по тексту файла. Если хост собирает несколько окружений Vite одним билдом, отчёт MUST считаться по CSS всех окружений и не зависеть от их порядка: объявленные классы — из CSS всех окружений, размеры слоёв — с одного (клиентские окружения первыми, далее по имени); окружение без CSS-ассетов в итог не входит. Отчёт пишется в `outDir` клиентского окружения и переписывается, когда окружение, собранное позже, меняет итог; строка сборки печатается заново, если изменилась. |
| A-20 | Отчёт MUST вычисляться теми же функциями, что и эмиссия (INV-DIAG-1). Категории «мёртвая safelist-запись» и «ассет не опознан» из v1 становятся прямыми фактами отчёта, а не эвристиками по собранным файлам. |

## 11. Рантайм (`./runtime`)

| ID | Требование |
|---|---|
| RT-1 | `createThemeController(manifest, options)` переключает **режим** активной темы: `mode`, `modes()`, `setMode(name, { persist? })`, `theme` (только чтение). Пишет `activation.attribute` со значением пары. Хранит в `storageKey` (по умолчанию `granum-theme`) имя **режима**, а не пары: смена темы на сборке не сбрасывает выбор пользователя. `initial: 'auto'` — сохранённый режим → `prefers-color-scheme` (первый режим с подходящим `colorScheme`) → `defaultMode`. DOM типизирован структурно, зависимостей нет. `persist: false` применяет режим без записи в хранилище. Ошибки хранилища на чтении и записи контроллер глотает: выбор тогда не запоминается. |
| RT-2 | Манифест контроллера MUST быть совместим с выводом `virtual:granum/themes` (T-4). |
| RT-3 | `createThemeScript({ manifest, storageKey?, nonce?, cookie?, reapplyOn? })` — чистая функция, возвращает `<script>` для `<head>`, который ставит пару до первого кадра; `createThemeScriptCode(...)` — тот же код без тега, для хоста, вставляющего скрипт сам. Правило выбора MUST совпадать с `initial: 'auto'` контроллера (RT-1, RT-5): пара на корне остаётся; иначе режим из cookie (только при `cookie`), из `localStorage`, первый режим системной схемы, режим по умолчанию. Код MUST собираться под манифест — пары и выбор по схеме константами, ветки cookie и `reapplyOn` только по опции — и MUST NOT выпускать исключение. На теме из двух режимов он SHOULD укладываться в 512 Б со всеми опциями. `reapplyOn` — события `document`, после которых пара ставится заново (хост, подменяющий документ без перезагрузки: `astro:after-swap`); подписка не дублируется. Имя cookie — токен RFC 6265, иначе ошибка; манифест без режимов — ошибка. Плагин MAY подставлять скрипт через `transformIndexHtml` (опция); SSR-приложение вставляет его само. Опция плагина — `granum(config, { themeScript: true | { storageKey?, nonce?, cookie?, reapplyOn? } })`: скрипт встаёт первым в `<head>` HTML-точки входа. |
| RT-4 | Адаптер хранилища на cookie — `createCookieStorage({ name?, maxAge?, path?, sameSite? })`: сервер читает режим из заголовка запроса (`modeFromCookie(manifest, cookieHeader, name?)`) и отдаёт `<html <attr>="<пара>">` с атрибутами `themeRootAttributes(manifest, mode)` — тогда скрипт не нужен (INV-MODE-6, INV-MODE-7). |
| RT-5 | Контроллер, поднятый поверх уже применённой пары, распознаёт режим по значению атрибута и не трогает корень. |
| RT-6 | `themeModeValue(manifest, mode, theme?)` отдаёт пару режима активной темы или темы превью из манифеста — для острова или превью на поддереве — и `undefined`, если пары нет в CSS сборки: значение, собранное по шаблону, молча не совпало бы ни с одним селектором. |
| RT-7 | `createThemeManifest({ theme, modes, defaultMode, activation? })` MUST собирать манифест режимов по описанию темы тем же правилом пары (A-28, `themePairValue`) и тем же порядком (режим по умолчанию первым, T-9), что сборка: для потребителя без `virtual:granum/themes` — CSS темы подключён готовым листом (T-16). Режим по умолчанию вне списка — ошибка. |

## 12. Диагностика и CLI (`bin/granum`, `./node`)

| ID | Требование |
|---|---|
| D-1 | Команды: `doctor`, `explain <providerId:Name>`, `why-css <class>`, `tokens <providerId:Name> [--deep]`, `themes`, `prune`, `report`, `codegen [<package-dir>] [--check]`, `audit [<dist-dir>]`. Команды приложения принимают путь к `granum.config.*`; `codegen` работает в пакете-провайдере со стандартными целями B-14 (`barrel`, `exports`, `manifest`, `registry`). Все принимают `--json`. |
| D-2 | `doctor` MUST проверять: валидность и версии манифестов, наличие файлов, на которые они ссылаются, граф провайдеров и компонентов, конфликты токенов с цепочкой источников (`token-conflict` — два пакетных слоя, данные темы или токены компонентов, на один токен в одном режиме; значения приложения перекрывают пакет намеренно, режимы `define` — копии базы и повторно не считаются), `token-undefined`, `safelist-redundant`, `component-mode-missing` (литерал компонента в режиме сборки взят из режима по умолчанию: файла ни этого режима, ни его предков у компонента нет, A-24; формула с `var(` следует ролям режима и находкой не считается), границу browser/node на бандле провайдера (B-16), нарушения раскладки. Выход `1` при `error`; `--strict` — и при `warn`. |
| D-3 | `why-css <class>` MUST отвечать по карте `matched` движка и манифестам: каким правилом, из какого источника, из какого компонента или файла приложения класс пришёл. |
| D-4 | Все команды MUST работать без сборки приложения, только по манифестам и конфигу; исключение — `report`, читающий `granum-report.json` собранного приложения. |
| D-5 | Форматтеры `format*Report` и функции `granum*` MUST экспортироваться из `./node` для программного использования. |
| D-6 | Имена, собранные в рантайме, MUST NOT становиться токенами: `var(--gr-${'{'}tone${'}'}-text)` не даёт токена `--gr-`. Сканер токенов MUST срезать комментарии тем же хелпером, что экстрактор классов (INV-ENG-5): документация про токен — не его потребление. |
| D-7 | `doctor --strict` MUST принимать `--allow=<code,code>` — коды, находки которых печатаются и считаются, но гейт не роняют (записанный долг). Без этого шва потребитель заводит обёртку вокруг доктора, и она расходится с доктором. |
| D-9 | `audit [<dist-dir>]` MUST проверять **собранный** дистрибутив: вырезан ли невыбранный компонент целиком (его уникальные классы, его собственный CSS), доехало ли всё, что обещала селекция, и не осталось ли недостижимых токенов, которые план обрезки назвал удаляемыми (`prune.removable` при `pruneTokens.mode: 'on'`). Классы селекторов CSS MUST читаться с полным экранированием движка: hex-код с пробелом (`.\32 xl\:p-4`) и не-ASCII как есть. Конфиг команде не нужен: селекция и провайдеры берутся из отчёта сборки (при его отсутствии — из ключей селекции), состав компонентов и объявленные токены — из манифестов провайдеров. Вердикт MUST выноситься по CSS: раскладку JS-чанков выбирает бандлер, а granum на JS не влияет (A-7), поэтому присутствие класса в JS — сведение, а не находка. Находкой быть MUST NOT: класс невыбранного компонента, которым пользуется и выбранный — в `classes` или в `safelist` (он приехал по праву); класс из разметки самого приложения; класс, которому движок не нашёл правила (о нём говорит `unmatched`); недостижимый токен при обрезке `off` или `report`, а при `on` — сохранённый планом обрезки (`keep`, `dynamicTokens`, override, структурный): это сведение; объектный провайдер — у него нет пакета с манифестом, это тоже сведение. Находки отчёта сборки (класс без правила, токен без объявления) MUST доводиться до кода возврата только с `--strict`: без него ими занимается `doctor`. Если в отчёте нет `classes.app` (отчёт постарше), аудит MUST отказаться судить об утечке классов: отдельный список с причиной и без влияния на код возврата. Само поле `classes.app` MUST нести только классы разметки, которые есть и у компонентов графа — включая невыбранные: именно их аудит и исключает, а полный словарь разметки на дизайн-системе — это десятки тысяч имён в каждом отчёте. Код возврата `1` при любой находке — команду MUST быть можно поставить в прогон другого репозитория (INV-DIST-1). Пустая селекция при списке провайдеров в отчёте MUST NOT быть ошибкой: проверяется, что компоненты пакетов не доехали; отчёт без селекции и без списка провайдеров — ошибка. |
| D-10 | `themes` MUST перечислять каталог тем графа: id, `title`, `extends`, режимы, `defaultMode`, `docs`, владельца — по индексу манифеста, не читая данных тем (C-29). `doctor` показывает активную тему, режимы и их источники. |
| D-11 | `tokens <providerId:Name> --deep` MUST показывать цепочку слоёв T-7 по каждому режиму, включая тему-источник токенов компонента (`ink → paper`) и режим-источник (`dim → dark`). |
| D-8 | Текстовый вывод `doctor` MUST оставаться читаемым на дизайн-системе из десятков компонентов: ошибки — целиком и первыми; предупреждения — сводкой по кодам с числами, в порядке серьёзности; перечисление внутри находки — свёрнутым до счётчика; список компонентов — свёрнутым до сумм. Детали MUST быть доступны флагами `--code=<code>`, `--component=<providerId:Name>`, `--components`. `--json` не сворачивает ничего. |

| цикл в `provider.dependencies` | `CircularProviderDependencyError` | регистрация |
| строковая зависимость не удовлетворена | `UnresolvedProviderDependencyError` | регистрация |
| ключ селекции не `providerId:Name` | `InvalidComponentKeyError` | селекция |
| провайдер не зарегистрирован | `ProviderNotRegisteredError` | селекция |
| компонент не найден | `ComponentNotFoundError` (со списком имеющихся; `partOf` — владелец, если ключ назвал часть составного компонента) | селекция |
| цикл в `component.dependencies` | `CircularDependencyError` (цепочка) | селекция |
| неучтённое ребро графа компонентов | `UndeclaredDependencyError` | сборка провайдера |
| `exports` без манифеста или subpath компонента | `PackageExportsError` | сборка провайдера |
| браузерный чанк импортирует node-entry granum или `node:` | `BoundaryViolationError` | сборка провайдера |
| CSS-файл манифеста отсутствует | `CssReadError` (провайдер, секция, субъект, `cause`) | сборка приложения |
| strict-разбор CSS-файла токенов не удался (файл `themesDir`, `tokensRef`) | `TokenParseError` внутри `TokenRefError` | сборка провайдера, сборка приложения |
| импорт компонента вне селекции при `guard: 'error'` | `ComponentOutsideSelectionError` (импортёр; `part` — часть, через подпуть которой импортирован владелец) | сборка приложения |
| импорт компонента из корня пакета-провайдера или корня целиком при `guard: 'error'` | `ComponentRootImportError` (провайдер, компоненты, импортёр) | сборка и dev приложения |
| тот же инстанс `granum()` во второй отдельной сборке (окружения одного builder Vite — одна сборка) | `PluginInstanceReusedError` (оба `outDir`) | разрешение конфига второй сборки |
| форма конфига невалидна | `InvalidConfigError` (путь до поля) | загрузка конфига |
| `@apply` не раскрывается: класс без правила, вариант (селекторный или через at-rule), класс из нескольких правил, вложенный контекст | `ApplyExpansionError` (`reason`) | сборка провайдера |
| ссылка на CSS с неподдержанной схемой или битым `data:`-URL | `CssSourceError` (`reason`) | сборка провайдера, сборка приложения |
| `granum.config.*` не загружается или не отдаёт конфиг | `ConfigLoadError` | CLI |
| codegen: несовпадение имени экспорта, маркеры, `exports` | `GranumCodegenError` (`reason` как в v1) | codegen |

Предупреждения (не ошибки) живут в трёх местах и не смешиваются:

- **манифест провайдера** (`warnings[]`, пишет сборка): `safelist-redundant`,
  `css-double-delivery`, `peer-missing`, `engine-module-missing`;
- **резолюция** (`warnings`, читает отчёт и `doctor`): `provider-without-manifest`,
  `provider-scanned`, `override-skipped`, и предупреждения тем и режимов —
  `component-theme-unknown`, `mode-extends-unresolved`, `mode-extends-cycle` —
  `doctor` показывает их своими кодами; подготовка
  приложения добавляет `app-sources-unset` — его видят отчёт и строка сборки;
- **`doctor`** (`diagnostics[]`, уровни `error` и `warn`): `missing-file`,
  `apply-not-expanded`, `boundary`, `important-in-provider-css`, `safelist-dead`,
  `token-undefined`, `token-conflict`, `unused-provider`, `provider-dialect-mismatch`,
  `provider-classes-recovered`, `provider-classes-dropped`, `engine-rules-skipped`,
  `subcomponents-missing` плюс всё, что доносится из манифеста и резолюции.

Расхождение отпечатков словаря само по себе предупреждением НЕ является: так
выглядит любое приложение с собственным правилом в фабрике движка. Предупреждает
разница наборов после пересчёта, а факт пересчёта виден полями отчёта
`providers[].reason` и `providers[].classes`.

Классы без правила и план обрезки токенов именованными предупреждениями НЕ
являются: это поля отчёта сборки — `classes.unmatched` (с источниками) и
`prune.removable` / `prune.kept` (A-19).

## 15. Совместимость и миграция с пресетом v1

### 15.1 Что сохраняется

- Семантика контракта: id, зависимости двух форм, селекция и её ключи, post-order DFS,
  активный набор тем, приоритет слоёв токенов, `strictTokens`, `group`.
- Раскладка `components/<Name>/index.js` и `groups/<g>/shared/`.
- Диагностические команды и их смысл.
- Рантайм тем.

### 15.2 Что меняется в контракте

| v1 | granum | Причина |
|---|---|---|
| `packageBaseUrl` обязателен, вычисляется провайдером | не нужен: база = директория манифеста, найденная через `exports` | убирает класс ошибок с `data:`-URL и «база на уровень выше» |
| `cssFiles` абсолютные URL + `cssFileAssetNames` позиционный fallback | один относительный путь в манифесте | fallback был компенсацией отсутствия манифеста |
| `styleAssetFileName` | удалено | было deprecated в v1 |
| `unocss: { rules, variants, preflights }` | `engine: { dialect, rules, variants, preflights }` в типах granum | независимость от UnoCSS, а словарь классов пакета назван |
| `tokenDefinitionsRef` читается приложением | токены компонента по темам (`themesDir`) материализуются на сборке провайдера в манифест | считать один раз там, где данные родились |
| safelist ∩ статика — не проверяется | `safelist-redundant` | молчаливых поломок нет |
| `undeclared-dependency` — эвристика по тексту, `warn` | по графу модулей бандлера, `error` | точность |
| `layer: 'granular'` с порядком −50 | каскадные слои `granum.*` | порядок объяснён именами |
| ключ токена с `--` → `----x` молча | `InvalidTokenKeyError` | молчаливых поломок нет |
| `themes.themeFiles`, `baseFile`, `tokensFile` — подмена файлов провайдера | нет: значения режима меняют `modes.tokenOverrides`, тему целиком — тема-объект приложения в `theme` (A-22) | данные провайдера остаются единственным источником его темы |
| `scan.*` опции приложения | нет: `node_modules` не обходится глобом; при расхождении отпечатков словаря читаются только файлы, названные манифестом (E-16) | манифест |

### 15.3 Миграция провайдера

1. Заменить импорт `@feugene/unocss-preset-granular/contract` → `@feugene/granum/contract`,
   `defineGranularComponent` → `defineGranumComponent`, `defineGranularProvider` →
   `defineGranumProvider`.
2. Убрать `packageBaseUrl`, `cssFileAssetNames`, `styleAssetFileName`; `unocss` → `engine` с объявленным `dialect`.
3. В `vite.config.ts` заменить три хелпера и ручные entry на `granumProvider()`.
4. Запустить `granum codegen` и `granum doctor --strict`.

### 15.4 Миграция приложения

1. Удалить `uno.config.ts`, `unocss`, `@unocss/*`, импорты `virtual:uno.css`.
2. Создать `granum.config.ts`, добавить `granum()` в `vite.config.ts`.
3. Заменить `virtual:uno:granular.css` + `virtual:uno.css` на `virtual:granum.css`.
4. Проверить отчёт сборки: `unmatched` должен быть пуст или объяснён.

## 18. Стабильность контракта (с 1.0)

До 1.0 ломать было дёшево: потребитель один и он наш. С 1.0 это кончается:
перечисленное ниже меняется только мажором и только с записью в `MIGRATION.md`.
Периода поддержки прежнего формата не будет и после 1.0 — мажор правит сразу
«как надо», но теперь об этом говорят вслух и заранее.

### 18.1 Что заморожено

| Что | Где зафиксировано |
|---|---|
| Контракт провайдера: форма дескрипторов, `GRANUM_CONTRACT_VERSION = 2` | §5, `./contract` |
| Формат манифеста (версия 3), его имя и ключ `exports["./granum.manifest.json"]` | §7, `manifest.md` |
| Точки входа пакета и их границы browser/node | §4.2 |
| Форма `GranumConfig` и значения по умолчанию | §10 |
| Имена и порядок слоёв `granum.{tokens,base,themes,components,utilities}` | §11, INV-CSS-1 |
| Идентификаторы виртуальных модулей и их типы в `./client` | §11, `client.d.ts` |
| Контракт движка `GranumEngine` и синтаксис диалекта `<vendor>/<vocabulary>@<major>` | §9, ADR-8 |
| Имена команд CLI, их коды возврата и коды диагностик (их пишут в `--allow`) | §12 |
| Имена и смысл полей отчёта сборки; новые поля добавлять можно | §12 |
| Классы ошибок и их поля | §14 |

### 18.2 Что не заморожено

* **Отпечаток словаря движка.** Он меняется при любом изменении набора правил —
  включая обновление вендоренного UnoCSS в `granum-engine-wind`, — и это не ломающее
  изменение ядра: пересчёт классов — штатный путь (A-E3, ADR-9). Совместимость
  словарей никогда не вычисляется и не обещается.
* **Тексты диагностик и формат печати CLI.** Гейты строятся на кодах и кодах
  возврата, а не на строках; `--json` для того и есть.
* **Строка времени сборки** (`time N ms (...)`) — диагностика, а не интерфейс: состав
  фаз может меняться.
* **Внутренности `./node`**, не описанные в ТЗ: это инструменты для наших скриптов,
  а не публичный API потребителя.
* **Цифры веса и времени.** Гейты стендов сверяют факты, а не байты и не
  миллисекунды (N-4, N-5).

### 18.3 Что это значит для пакетов-провайдеров

Манифест, собранный granum 1.x, читается любым granum 1.x — и более старшим, и
более младшим. Поэтому peer-диапазон провайдера разумно держать широким
(`>=1.0.0 <2.0.0`), а не прибивать к минору: приложение выбирает версию само.

### 18.4 Что меняется в 3.0

Темы и режимы ([ADR-11](./decisions.md)) ломают замороженную поверхность — отсюда мажор и запись в
`MIGRATION.md`.

| Что | Изменение |
|---|---|
| Контракт провайдера | версия `1 → 2`: `theme` — каталог и реестр (§5.3), `themesDir` компонента (C-33); `tokenDefinitions*` удалены (C-38) |
| Манифест | формат `2 → 3`: `theme.catalog`, `theme.registry`, `components.*.tokens.themes`; формат 2 без тем читается (M-11) |
| `GranumConfig` | `themes` → `theme`, `previews`, `modes` (A-22…A-33) |
| Граф провайдеров | строковая зависимость подгружает донора (A-31) |
| Виртуальный модуль | `virtual:granum/themes` — новая форма (T-4), id прежний |
| Рантайм | `createThemeController` переключает режим (RT-1), `createThemeScript` — новое (RT-3) |
| Коды диагностики | §14: предупреждения тем → предупреждения режимов, новые ошибки тем |
| Поля отчёта | `themes { theme, themeSource, modes, modesSource, previews }` (A-19) |
| Движок | `EngineInput.darkSelector` — аддитивно (E-20) |
| Имена слоёв | без изменений |
