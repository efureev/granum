Конвейер Granum

Новый пакет: @feugene/granum. Сейчас конфиг UnoCSS является оркестратором: мы описываем наш конвейер внутри чужого. Целевая архитектура переворачивает это: наш резолвер и наш Vite-плагин ведут данные от исходников провайдера до дистрибутива приложения, а движок утилит становится отдельным пакетом, который выбирает приложение.

Как это устроено сейчас

Провайдер собирает dist по нашей раскладке, а всё остальное происходит в uno.config.ts приложения. Пресет отдаёт UnoCSS готовый CSS, safelist и globs, после чего UnoCSS сам сканирует node_modules и генерирует утилиты. JS-ветка живёт отдельно и от селекции компонентов не зависит.

Три следствия этой схемы:

  • Оркестрация чужая. Порядок слоёв, скан контента, safelist и виртуальные модули существуют в терминах UnoCSS. Даже то, что пресет умеет вернуть content, UnoCSS игнорирует, и нужен костыль granularContent в пользовательском конфиге.
  • Классы извлекаются на стороне приложения. Каждая сборка приложения заново читает собранные чанки провайдера из node_modules, хотя набор классов компонента известен уже при публикации пакета.
  • Селекция управляет только CSS. Токены, темы и CSS компонентов идут из одной резолюции, а JS в неё не входит: одна и та же селекция не гарантирует согласованности бандла.

Целевая архитектура

Точка передачи между провайдером и приложением становится явной: манифест, который провайдер публикует вместе с пакетом. Всё, что можно посчитать при сборке провайдера, считается там один раз. Приложение читает манифесты, строит одну резолюцию и из неё кормит три канала: JS, CSS и токены.

Блоки и их задачи

Порядок совпадает с движением данных. В графе «есть сейчас» перечислено то, что переносится в новую архитектуру без переписывания.

Ожидаемый результат

Автору провайдера

  • Один плагин в vite.config.ts вместо трёх хелперов и ручного списка entry.
  • Классы и токены компонента фиксируются при публикации: пакет несёт доказательство того, что он потребляет.
  • Компоненты по-прежнему пишутся утилитами и дизайн-токенами; синтаксис классов не меняется.

Приложению

  • Один конфиг, одна зависимость на пресет. Без uno.config.ts и без unocss.
  • Холодная сборка не читает node_modules: набор классов известен из манифестов.
  • Селекция компонентов даёт согласованный бандл: JS, CSS и токены из одной резолюции.
  • CSS с каскадными слоями, где порядок объяснён именами, а не числами.

Репозиторию

  • Ядро, контракт, рантайм и движок без внешних зависимостей; плагины зависят только от vite.
  • Критерий совместимости: CSS стенда bench-one совпадает с текущим по правилам, JS без изменений.
  • unocss-mini-extra-rules становится частью движка.

Решения, которые нужно принять до ТЗ

  • Где генерировать утилиты по умолчанию. В приложении даёт дедупликацию и общую шкалу темы; в провайдере даёт пакеты, пригодные без нашего плагина вовсе. Предложение: в приложении, режим «прекомпиляция» опцией провайдера.
  • Объём правил движка. preset-mini покрывает то, чем пользуются провайдеры сейчас; preset-wind4 в полтора раза больше. Предложение: mini плюс наши extra-rules, wind4 не тащить.
  • Судьба @apply. Раскрывать при сборке провайдера своим кодом для плоских правил либо оставить css-tree как единственную внешнюю зависимость плагина сборки. Предложение: своё раскрытие для плоских правил, вложенные конструкции запрещены контрактом.
  • Каскадные слои против порядка конкатенации. @layer поддержан всеми актуальными браузерами, но меняет специфичность для приложений, которые ещё пишут CSS без слоёв. Предложение: слои, с опцией плоской эмиссии.
  • Формат манифеста. JSON рядом с dist или JS-модуль с типами. Предложение: JSON как источник, типизированный доступ через /contract.

Границы

  • Движок утилит не пишется с нуля: правила и генератор берутся форком, интерфейс адаптера наш.
  • Бандлер не заменяется. Минификация и tree-shaking JS остаются работой rolldown; наш вклад в JS-канал — раскладка, entry по селекции и проверка импортов.
  • Контракт провайдера версии 1 остаётся читаемым: миграция провайдеров сводится к замене одного импорта и добавлению плагина сборки.
