# Архитектурные решения

Формат: контекст → варианты → решение → последствия → до какого этапа плана можно
пересмотреть. Решение «по умолчанию» действует, пока не изменено правкой этого файла.

## ADR-1. Где генерируются утилиты

**Контекст.** Классы компонентов известны при сборке провайдера (манифест). Утилиты можно
генерировать либо в приложении, либо у провайдера (компонент публикуется с готовым CSS).

**Варианты.**
1. В приложении. Одна шкала темы на всё приложение, дедуп между провайдерами и
   приложением, override шкалы приложением. Требует нашего плагина у потребителя.
2. У провайдера. Пакет пригоден без плагина granum (обычный `import 'pkg/styles.css'`).
   Дублирование одинаковых утилит между пакетами и приложением, нет override шкалы,
   safelist генерируется провайдером без знания о приложении.
3. Оба через один движок; режим выбирает провайдер (`precompile: true`).

**Решение.** Вариант 1 по умолчанию; вариант 3 заложен в манифест (поле `css` компонента
может содержать сгенерированный `utilities.css`, а `classes` тогда пусты) и реализуется
после первого релиза.

**Последствия.** Интерфейс движка обязан быть пригодным для обоих мест запуска (E-7).
Манифест не различает «стили компонента» и «прекомпилированные утилиты» кроме как
по имени файла; при прекомпиляции `classes` пусты, чтобы приложение не сгенерировало
их второй раз.

**Пересмотр.** До этапа 5 плана.

## ADR-2. Движок: форк ядра UnoCSS, не с нуля и не peer

**Контекст.** Нужно превращать `p-4`, `bg-[var(--x)]`, `hover:…` в CSS. Своё с нуля —
объём, сопоставимый со всем пакетом v1, и постоянная гонка за Tailwind-семантикой.
Peer на `unocss` — сохраняет чужой оркестратор и зависимости у приложения.

**Варианты.**
1. Вендорить `@unocss/core` (1.3k строк dist), `@unocss/preset-mini` (3.8k),
   `@unocss/rule-utils` (0.7k, минус `magic-string`), `extractor-arbitrary-variants`
   (65). Итого ≈ 6k строк, MIT, ноль внешних зависимостей.
2. Вендорить `preset-wind4` (6.3k) вместо `mini`.
3. Peer на `unocss` за адаптером.

**Решение.** Вариант 1, версия 66.7.5, плюс правила `@feugene/unocss-mini-extra-rules`,
перенесённые на внутренние типы. `@unocss/vite` и `transformer-directives` не берутся.
Вендоренный код лежит в `src/engine/vendor/` с `THIRD_PARTY_NOTICES.md` и порождается
скриптом `scripts/vendor-unocss.mjs` из `dist` пакетов; правки в него допускаются только
через список патчей в этом скрипте (каждый обязан примениться ровно один раз), чтобы
обновление с апстрима оставалось возможным. Берутся собранные `dist`, а не исходники:
их `.d.ts` не проверяются нашим строгим `tsconfig` (`skipLibCheck`), и апстримный код
не нужно приводить к нашим правилам.

**Последствия.** Форк замораживается; апстримные правки правил портируются вручную по
мере необходимости. Golden-тесты (E-5) фиксируют поведение. IDE-плагин UnoCSS и
инспектор недоступны; `why-css` и отчёт частично их заменяют.

**Пересмотр.** До этапа 2 плана. Переход на wind4 — совместимое расширение позже.

## ADR-3. `@apply` раскрывается у провайдера, без `css-tree`

**Контекст.** `transformer-directives` тянет `css-tree` (внешняя зависимость).
`@apply` встречается в CSS компонентов провайдеров и в `<style>` SFC.

**Варианты.**
1. Вендорить `css-tree` (большой) ради `@apply`.
2. Своё раскрытие для плоских правил: `@apply a b c;` внутри блока с селектором →
   декларации утилит из движка; вложенные конструкции и `@screen`/`theme()` —
   не поддерживаются, ошибка сборки провайдера.
3. Не поддерживать `@apply` вовсе.

**Решение.** Вариант 2, только на сборке провайдера (B-11). В приложении `@apply` в
собственном CSS — вне объёма granum (это забота обычного CSS-инструментария).

**Последствия.** Контракт ограничивает `@apply` плоскими правилами; `doctor` ловит
остаточные директивы в `dist` (`apply-not-expanded`). Фикстура `XTest1` с `@apply`
переносится и служит тестом.

**Пересмотр.** До этапа 4 плана.

## ADR-4. Каскадные слои CSS вместо порядка конкатенации

**Контекст.** В v1 порядок «утилита перебивает базу компонента» держался на числе `−50`
в терминах слоёв UnoCSS. Нужен порядок, объяснимый именами и не зависящий от движка.

**Варианты.**
1. `@layer granum.tokens, granum.base, granum.themes, granum.components, granum.utilities;`
   Нелейерный CSS приложения по спецификации побеждает все слои — «последнее слово за
   приложением» бесплатно.
2. Плоская конкатенация в том же порядке; порядок держится на позиции в файле.

**Решение.** Вариант 1 по умолчанию, вариант 2 как `css.layers: false` для приложений с
нелейерным CSS, где смена специфичности нежелательна (A-14). Имена слоёв — с префиксом
`granum.` (вложенные слои), чтобы приложение могло объявить свой внешний порядок
`@layer reset, granum, app;`.

**Последствия.** Правило `!important` внутри слоёв инвертирует порядок (по спецификации);
контракт запрещает `!important` в CSS провайдеров, `doctor` предупреждает
(`important-in-provider-css`). Замер веса режется по слоям, а не по именам файлов.

**Пересмотр.** До этапа 5 плана.

## ADR-5. Манифест — JSON в `dist`, экспортируемый через `exports`

**Контекст.** Нужна точка передачи «пакет → приложение», не зависящая от бандлера и от
`packageBaseUrl`.

**Варианты.**
1. `dist/granum.manifest.json` + `exports["./granum.manifest.json"]`; приложение находит
   его через `import.meta.resolve`. База путей — директория файла.
2. JS-модуль `granum-provider.js`, экспортирующий объект (как в v1). Требует
   `packageBaseUrl`, уязвим к подмене `new URL` бандлером, не читается без исполнения.
3. Поле в `package.json`.

**Решение.** Вариант 1. Правила движка провайдера (код) — отдельный модуль по пути из
манифеста (`engineModule`). Объектная форма провайдера сохраняется только для тестов и
локальной разработки без сборки.

**Последствия.** Исчезает класс ошибок с `packageBaseUrl` (INV-LAY-3 остаётся как
проверка на бандле). Диагностика работает по файлам, без исполнения кода пакета.
Типизированный доступ — через `readManifest` из `./node` и тип `GranumManifest` из
`./contract`.

**Пересмотр.** До этапа 3 плана.

## ADR-6. Селекция: явный список по умолчанию, `'imports'` как второй режим

**Контекст.** В v1 селекция задаётся списком; JS от неё не зависит. Хочется, чтобы
достаточно было импортировать компонент.

**Варианты.**
1. Только явный список + guard.
2. Только вывод из импортов (статический скан `appSources`).
3. Оба: список по умолчанию, `'imports'` опцией; guard связывает их в обе стороны.

**Решение.** Вариант 3. Статический скан импортов — по спецификаторам
`<providerId>/components/<Name>` и именованным импортам из `virtual:granum/components`;
динамические импорты с вычисляемыми строками не поддерживаются и требуют явного списка.

**Последствия.** Появляется INV-SEL-5. Режим `'imports'` требует `appSources.dirs`.

**Пересмотрено 2026-09-26 (0.1.0): рекомендуемым остаётся явный список.**
Скан текстовый, и компонент, отрисованный по вычисленному имени
(`<component :is="name">`, имя из данных), он не находит — приложение молча
теряет его CSS, причём guard такой случай тоже не видит: статического импорта
нет. Явный список, наоборот, держит селекцию в одном месте, где её видно на
ревью. `'imports'` остаётся поддержанным вторым режимом и уместен там, где
набор компонентов часто меняется; скан PascalCase-тегов (A-8) делает его
пригодным для авто-импорта, когда импортов в исходниках нет вовсе.

Что изменит решение: способ объявить компонент, отрисованный динамически (без
возврата к полному списку), и приложение репозитория, живущее на `'imports'` —
сейчас режим покрыт юнит- и интеграционными тестами (`prepareApp`, `emitCss`,
`vitePlugin` со настоящей сборкой, скан тегов в `autoImport`), но ни одного
стенда на нём нет.

## ADR-7. Новый репозиторий и новый пакет, а не мажорная версия v1

**Контекст.** Меняются оркестратор, точка передачи, контракт (§15.2) и имя.

**Решение.** Отдельный репозиторий `granum` с тем же типом монорепо (Yarn 1 workspaces):
пакет, фикстурные провайдеры, приложения-тесты, стенды. Пресет v1 не изменяется и
получает только заметку о преемнике в README после первого релиза granum.

**Последствия.** Снапшот CSS `bench-one` с v1 копируется в репозиторий granum один раз
(AC-2) и обновляется вручную.
