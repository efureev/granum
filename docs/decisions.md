# Архитектурные решения

Формат: контекст → варианты → решение → последствия → до какого этапа плана можно
пересмотреть. Решение «по умолчанию» действует, пока не изменено правкой этого файла.

## ADR-1. Где генерируются утилиты

**Контекст.** Классы компонентов известны при сборке провайдера (манифест). Утилиты можно
генерировать либо в приложении, либо у провайдера (компонент публикуется с готовым CSS).

**Варианты.**
1. В приложении. Одна шкала темы на всё приложение, дедуп между провайдерами и
   приложением, override шкалы приложением. Требует нашего плагина у потребителя.
2. У провайдера. Пакет пригоден без плагина granum (обычный `import 'pkg/styles.css'`).
   Дублирование одинаковых утилит между пакетами и приложением, нет override шкалы,
   safelist генерируется провайдером без знания о приложении.
3. Оба через один движок; режим выбирает провайдер (`precompile: true`).

**Решение.** Вариант 1 по умолчанию; вариант 3 заложен в манифест (поле `css` компонента
может содержать сгенерированный `utilities.css`, а `classes` тогда пусты) и реализуется
после первого релиза.

**Последствия.** Интерфейс движка обязан быть пригодным для обоих мест запуска (E-7).
Манифест не различает «стили компонента» и «прекомпилированные утилиты» кроме как
по имени файла; при прекомпиляции `classes` пусты, чтобы приложение не сгенерировало
их второй раз.

**Пересмотр.** До этапа 5 плана.

## ADR-2. Движок: форк ядра UnoCSS, не с нуля и не peer

> Пресет в форке пересмотрен ADR-10: вместо `preset-mini` вендорится
> `preset-wind3`. Сам выбор «форк, а не с нуля и не peer» в силе.

**Контекст.** Нужно превращать `p-4`, `bg-[var(--x)]`, `hover:…` в CSS. Своё с нуля —
объём, сопоставимый со всем пакетом v1, и постоянная гонка за Tailwind-семантикой.
Peer на `unocss` — сохраняет чужой оркестратор и зависимости у приложения.

**Варианты.**
1. Вендорить `@unocss/core` (1.3k строк dist), `@unocss/preset-mini` (3.8k),
   `@unocss/rule-utils` (0.7k, минус `magic-string`), `extractor-arbitrary-variants`
   (65). Итого ≈ 6k строк, MIT, ноль внешних зависимостей.
2. Вендорить `preset-wind4` (6.3k) вместо `mini`.
3. Peer на `unocss` за адаптером.

**Решение.** Вариант 1, версия 66.7.5, плюс правила `@feugene/unocss-mini-extra-rules`,
перенесённые на внутренние типы. `@unocss/vite` и `transformer-directives` не берутся.
Вендоренный код лежит в `src/engine/vendor/` с `THIRD_PARTY_NOTICES.md` и порождается
скриптом `scripts/vendor-unocss.mjs` из `dist` пакетов; правки в него допускаются только
через список патчей в этом скрипте (каждый обязан примениться ровно один раз), чтобы
обновление с апстрима оставалось возможным. Берутся собранные `dist`, а не исходники:
их `.d.ts` не проверяются нашим строгим `tsconfig` (`skipLibCheck`), и апстримный код
не нужно приводить к нашим правилам.

**Последствия.** Форк замораживается; апстримные правки правил портируются вручную по
мере необходимости. Golden-тесты (E-5) фиксируют поведение. IDE-плагин UnoCSS и
инспектор недоступны; `why-css` и отчёт частично их заменяют.

**Пересмотр.** До этапа 2 плана. Переход на wind4 — совместимое расширение позже.

## ADR-3. `@apply` раскрывается у провайдера, без `css-tree`

**Контекст.** `transformer-directives` тянет `css-tree` (внешняя зависимость).
`@apply` встречается в CSS компонентов провайдеров и в `<style>` SFC.

**Варианты.**
1. Вендорить `css-tree` (большой) ради `@apply`.
2. Своё раскрытие для плоских правил: `@apply a b c;` внутри блока с селектором →
   декларации утилит из движка; вложенные конструкции и `@screen`/`theme()` —
   не поддерживаются, ошибка сборки провайдера.
3. Не поддерживать `@apply` вовсе.

**Решение.** Вариант 2, только на сборке провайдера (B-11). В приложении `@apply` в
собственном CSS — вне объёма granum (это забота обычного CSS-инструментария).

**Последствия.** Контракт ограничивает `@apply` плоскими правилами; `doctor` ловит
остаточные директивы в `dist` (`apply-not-expanded`). Фикстура `XTest1` с `@apply`
переносится и служит тестом.

**Пересмотр.** До этапа 4 плана.

## ADR-4. Каскадные слои CSS вместо порядка конкатенации

**Контекст.** В v1 порядок «утилита перебивает базу компонента» держался на числе `−50`
в терминах слоёв UnoCSS. Нужен порядок, объяснимый именами и не зависящий от движка.

**Варианты.**
1. `@layer granum.tokens, granum.base, granum.themes, granum.components, granum.utilities;`
   Нелейерный CSS приложения по спецификации побеждает все слои — «последнее слово за
   приложением» бесплатно.
2. Плоская конкатенация в том же порядке; порядок держится на позиции в файле.

**Решение.** Вариант 1 по умолчанию, вариант 2 как `css.layers: false` для приложений с
нелейерным CSS, где смена специфичности нежелательна (A-14). Имена слоёв — с префиксом
`granum.` (вложенные слои), чтобы приложение могло объявить свой внешний порядок
`@layer reset, granum, app;`.

**Последствия.** Правило `!important` внутри слоёв инвертирует порядок (по спецификации);
контракт запрещает `!important` в CSS провайдеров, `doctor` предупреждает
(`important-in-provider-css`). Замер веса режется по слоям, а не по именам файлов.

**Пересмотр.** До этапа 5 плана.

## ADR-5. Манифест — JSON в `dist`, экспортируемый через `exports`

**Контекст.** Нужна точка передачи «пакет → приложение», не зависящая от бандлера и от
`packageBaseUrl`.

**Варианты.**
1. `dist/granum.manifest.json` + `exports["./granum.manifest.json"]`; приложение находит
   его через `import.meta.resolve`. База путей — директория файла.
2. JS-модуль `granum-provider.js`, экспортирующий объект (как в v1). Требует
   `packageBaseUrl`, уязвим к подмене `new URL` бандлером, не читается без исполнения.
3. Поле в `package.json`.

**Решение.** Вариант 1. Правила движка провайдера (код) — отдельный модуль по пути из
манифеста (`engineModule`). Объектная форма провайдера сохраняется только для тестов и
локальной разработки без сборки.

**Последствия.** Исчезает класс ошибок с `packageBaseUrl` (INV-LAY-3 остаётся как
проверка на бандле). Диагностика работает по файлам, без исполнения кода пакета.
Типизированный доступ — через `readManifest` из `./node` и тип `GranumManifest` из
`./contract`.

**Пересмотр.** До этапа 3 плана.

## ADR-6. Селекция: явный список по умолчанию, `'imports'` как второй режим

**Контекст.** В v1 селекция задаётся списком; JS от неё не зависит. Хочется, чтобы
достаточно было импортировать компонент.

**Варианты.**
1. Только явный список + guard.
2. Только вывод из импортов (статический скан `appSources`).
3. Оба: список по умолчанию, `'imports'` опцией; guard связывает их в обе стороны.

**Решение.** Вариант 3. Статический скан импортов — по спецификаторам
`<providerId>/components/<Name>` и именованным импортам из `virtual:granum/components`;
динамические импорты с вычисляемыми строками не поддерживаются и требуют явного списка.

**Последствия.** Появляется INV-SEL-5. Режим `'imports'` требует `appSources.dirs`.

**Пересмотрено 2026-09-26 (0.1.0): рекомендуемым остаётся явный список.**
Скан текстовый, и компонент, отрисованный по вычисленному имени
(`<component :is="name">`, имя из данных), он не находит — приложение молча
теряет его CSS, причём guard такой случай тоже не видит: статического импорта
нет. Явный список, наоборот, держит селекцию в одном месте, где её видно на
ревью. `'imports'` остаётся поддержанным вторым режимом и уместен там, где
набор компонентов часто меняется; скан PascalCase-тегов (A-8) делает его
пригодным для авто-импорта, когда импортов в исходниках нет вовсе.

Что изменит решение: способ объявить компонент, отрисованный динамически (без
возврата к полному списку), и приложение репозитория, живущее на `'imports'` —
сейчас режим покрыт юнит- и интеграционными тестами (`prepareApp`, `emitCss`,
`vitePlugin` со настоящей сборкой, скан тегов в `autoImport`), но ни одного
стенда на нём нет.

## ADR-7. Новый репозиторий и новый пакет, а не мажорная версия v1

**Контекст.** Меняются оркестратор, точка передачи, контракт (§15.2) и имя.

**Решение.** Отдельный репозиторий `granum` с тем же типом монорепо (Yarn 1 workspaces):
пакет, фикстурные провайдеры, приложения-тесты, стенды. Пресет v1 не изменяется и
получает только заметку о преемнике в README после первого релиза granum.

**Последствия.** Снапшот CSS `bench-one` с v1 копируется в репозиторий granum один раз
(AC-2) и обновляется вручную.

## ADR-8. Движок — выбор приложения; диалект — контракт словаря

**Контекст.** ADR-2 поместил вендоренное ядро UnoCSS внутрь пакета и назвал его
`'builtin'`. Интерфейс движка при этом сменный, но диалект словаря нигде не
записан, а сборка провайдера фильтрует классы манифеста своим движком (B-6).
Пакет, собранный одним движком, и приложение с другим расходятся молча: класс,
который движок приложения сгенерировал бы, а движок пакета не знал, в манифест
не попал вовсе. Плюс правила непортируемы между генераторами, а контракт делал
вид, что их можно складывать в один.

**Варианты.**
1. Оставить как есть: один вендоренный движок, диалект неявный.
2. Записать диалект в манифест, движок оставить в ядре.
3. Записать диалект, движок вынести в отдельный пакет, приложение обязано его выбрать.
4. Разрешить цепочку движков в одной сборке.

**Решение.** Вариант 3. Диалект — имя словаря (`<vendor>/<vocabulary>@<major>`),
сравнение равенством; любая опция, меняющая набор генерируемых имён качественно,
меняет диалект. Машинное решение «верить списку классов или пересчитать» принимает
не диалект, а отпечаток словаря — см. [ADR-9](#adr-9-отпечаток-словаря-а-не-версия-реализации).
Манифест записывает и диалект, и отпечаток как факт о происхождении данных, оба
`null` — если пакет не зависит ни от какого словаря. Правила провайдера
исполняются только движком объявленного диалекта. Вендоренный форк уезжает в
`@feugene/granum-engine-wind` вместе с golden-тестом. ТЗ —
[`spec-engine.md`](./spec-engine.md), реализация — этап 8 плана.

Вариант 4 отвергнут, и обоснование именно такое, а не «ломает инварианты»:
атрибуцию вердикта инварианты выдерживают, а префиксы переменных, порядок
preflight и объединение экстракторов — инженерия. Блокирует одно — совпадение
имён при разном смысле. Маршрутизация по пакету заставляет оба движка выпустить
`.p-4` в один слой, и победит тот, чей блок лежит позже, сразу для обоих
пакетов; подслои не помогают, потому что слои CSS не дают разного старшинства
разным потребителям одного имени, а переименовать классы пакета нельзя — они
вкомпилированы в его чанки. Маршрутизация по классу с «первым совпавшим» прячет
конфликт совсем: класс сгенерирован, непокрытого нет, а отрисован он по чужому
словарю. Плюс сама цепочка нужна лишь тогда, когда у приложения нет движка с
более широким словарём, а у семейства UnoCSS и Tailwind он как раз есть, и
пересчёт классов измеряет, покрыл ли он каждый пакет. Форма расширения описана в
§15 ТЗ, если потребность появится.

**Последствия.** Ломающее изменение контракта: `engine` в конфиге обязателен и
принимает инстанс, `granumProvider` требует движок, версия формата манифеста —
2, `engineModule` переезжает в блок `engine`. Обратной совместимости нет
намеренно: `0.1.0` публиковался как проверка и потребителей не имеет. Апстримная
часть ADR-2 (какой именно форк, версия 66.7.5, порядок вендоринга) остаётся в
силе, меняется только адрес: пакет движка вместо `src/engine/vendor`.

**Пересмотр.** До этапа 8 плана.

## ADR-9. Отпечаток словаря, а не версия реализации

**Контекст.** ADR-8 разрезает мир по строке диалекта, и мажор в ней — часть
имени словаря. Но словарь внутри мажора не постоянен: апстрим добавляет правила
в минорах, приложение добавляет свои правила фабрике движка. Пакет, собранный
реализацией `66.7.5`, и приложение на `66.9.0` объявят один диалект
`unocss/preset-wind3+granum@66`; список классов в манифесте отфильтрован старой
реализацией, приложение пойдёт быстрым путём и не узнает, что его движок знает
имена, которых в списке нет. Это ровно та тихая потеря, от которой ADR-8 и
защищает, только загнанная в границы мажора.

**Варианты.**
1. Оставить сравнение по диалекту: дыра внутри мажора остаётся.
2. Включить версию реализации в сравнение: `name@version` различаются — пересчёт.
3. Разрешить пакету объявлять список совместимых диалектов.
4. Считать отпечаток фактического набора имён и решать по нему.

**Решение.** Вариант 4. Движок объявляет `vocabulary` — непрозрачную строку,
меняющуюся ровно тогда, когда меняется множество имён, которые он умеет
сгенерировать. Ядро даёт для этого `vocabularyFingerprint`: 64-битный
некриптографический хеш по идентификаторам правил и именам вариантов,
независимый от порядка. Доверие списку классов манифеста ключуется отпечатком;
загрузка правил провайдера — по-прежнему диалектом, потому что правило,
написанное для словаря, не ломается от того, что реализация знает больше имён.
Номер версии в решениях не участвует вовсе: он пишется в манифест для чтения
человеком.

Вариант 2 отвергнут, хотя и закрывает ту же дыру: он привязывает решение ко всей
версии, и патч, не добавивший ни одного правила, стоит приложению полного
пересчёта всех пакетов. Отпечаток различает эти случаи по существу — по правилам,
а не по номеру, — и потому работает в рамках мажора, как и задумано диалектом.
Вариант 3 отвергнут как непроверяемое обещание: автор утверждает совместимость,
не проверяет её никто, а расплачивается приложение непокрашенным компонентом.
Совместимость либо измерена пересчётом, либо не утверждается.

Отпечаток некриптографический намеренно: он ключует решение сборки, подделывать
его некому, а цена коллизии — один пропущенный пересчёт на 2^64 различных
словарей. Движок вправе объявить отпечаток своей строкой, если гарантирует
правило изменения сам.

**Последствия.** У `GranumEngine` появляется обязательное поле `vocabulary`, у
блока `engine` манифеста — одноимённое. Приложение с собственным правилом в
фабрике движка пересчитывает классы всех пакетов: это цена точности, она платится
один раз за сборку и кэшируется в памяти процесса. Появляется ветка «диалект
равен, отпечаток другой», у неё свой стенд (`app-2`) и свой код в отчёте.

**Пересмотр.** Если пересчёт окажется дорогим на большом графе пакетов —
ключевать дисковый кэш хешем манифеста и отпечатком; сам критерий доверия не
менять.

## ADR-10. Пресет в форке — `preset-wind3`, а не `preset-mini`

**Контекст.** Форк вендорил `preset-mini` плюс восемь семейств доп-правил —
перенос `@feugene/unocss-mini-extra-rules` из пресета v1. Набор собирался по
факту: каждое семейство закрывало дыру, на которую кто-то напоролся глазами.
Витрина granularity на восьми провайдерах показала, что так закрыты не все:
`border-collapse` (таблицы девяти графиков и календарь), `list-none`,
`touch-none`, `scroll-py-1` правил не имели ни в `preset-mini`, ни в доп-правилах.
Класс в разметке есть, CSS нет, сборка зелёная, видно только на живой странице.
Дыра пришла из v1 вместе с набором и жила там же незамеченной.

**Варианты.**
1. Дописать четыре семейства в доп-правила: закрывает эти четыре и оставляет
   механизм «ищем дыры глазами».
2. Вендорить `preset-wind3` вместо `preset-mini`: это тот же `preset-mini` плюс
   wind-правила, то есть словарь шире по построению.
3. Вендорить `preset-wind4`: словарь Tailwind v4.

**Решение.** Вариант 2. Проверено на настоящем наборе классов дизайн-системы
(1399 уникальных имён из восьми манифестов): `preset-wind3` без единого нашего
правила покрывает 1397 против 1393 у `preset-mini` с восемью семействами
доп-правил; непокрытыми остаются только два класса-метки (`peer`,
`group/segmented-item`), у которых CSS и не должно быть. Декларации при этом
расходятся у одиннадцати классов из 1399, и все одиннадцать разобраны в
CHANGELOG движка. Семь семейств доп-правил стали мёртвым кодом и удалены;
осталось одно — альфа на произвольном цвете (`bg-[var(--x)]/55`), которую wind3
молча теряет, и она же теперь единственная причина суффикса `+granum` в
диалекте.

Вариант 1 отвергнут: он лечит симптом. Набор, собираемый по замеченным дырам,
будет отставать от словаря всегда, а стоимость незамеченной дыры — компонент,
нарисованный не полностью, без единой ошибки в логе.

Вариант 3 отвергнут **на сейчас**, и не из-за размера: 876 классов из 1399 меняют
декларации. `preset-wind4` считает отступы через `calc(var(--spacing) * N)`,
радиусы и межстрочные — через переменные темы, а произвольный цвет оборачивает в
`color-mix(in oklab, … var(--un-bg-opacity), transparent)`. Дизайн-система красит
почти всё через `bg-[var(--gr-…)]`, то есть переезд на wind4 — это смена
механизма отрисовки каждой поверхности, а не расширение словаря. Плюс у wind4
свой reset в preflight, включённый по умолчанию. Форк всё равно заморожен на
66.7.5, поэтому «wind4 — будущее» сегодня ничего не даёт; когда семантика
Tailwind v4 понадобится осознанно, это будет второй движок со своим диалектом, и
механизм диалектов ровно для этого и заведён.

**Следствия.** Диалект сменился на `unocss/preset-wind3+granum@66`, пакет движка
переименован в `@feugene/granum-engine-wind`: «mini» в имени перестало описывать
содержимое. Вендор вырос на `preset-wind3` (140 kB) и по-прежнему включает
`preset-mini` — wind3 построен на нём и тянет его подпутями. Вес вывода на наборе
дизайн-системы: 15.83 kB gzip против 15.80 kB у прежнего движка.

## ADR-11. Тема — данные провайдера, режим — активация приложения

**Контекст.** Тема в granum 1.x–2.x — плоское имя набора токенов под селектором: `light` и
`dark` — две такие темы, в CSS приложения едут все активные, переключаются они в рантайме. Уровня
«дизайн-язык» нет. Дизайн-системе на granum понадобились несколько дизайн-языков с общим API
компонентов: базовый и три концепта, у каждого светлый и тёмный варианты, у приложения — свои
варианты поверх (`ocean` поверх тёмного). Плоскими именами это не выражается: N языков × M вариантов
дают N×M тем, в CSS едут все, полноту по словарю токенов не проверить, а «тёмный вариант другого
языка» — только соглашение об именах.

Разбор нашёл, что плоская модель уже течёт. Селекторы тем живут в файлах провайдера и расходятся с
тем, как тему включают: компонент дизайн-системы объявил тёмное значение только под `.dark`, а
переключение пишет `[data-theme='dark']`. Override темы-файла с селектором `:root` встаёт не в тот
слой и проигрывает файлу, хотя `granum tokens` показывает его значение. Файлы неактивных тем читаются,
вопреки INV-THM-5.

**Варианты.**
1. Оставить плоские темы и договориться об именах `<язык>-<вариант>`.
2. Два уровня: тема — дизайн-язык, режим — вариант внутри неё; тема — CSS-файлы провайдера, как
   сейчас.
3. Два уровня, тема — **данные** (значения токенов без селекторов), селекторы назначает приложение
   из активации режима; на корне — одно значение пары `data-theme="<тема>-<режим>"`.

**Решение.** Вариант 3.

- Тема — данные провайдера: каталог в манифесте, полные данные отдельным JSON на тему, реестр токенов
  `root | mode`, по которому сборка провайдера проверяет полноту темы. Наследование темы от темы
  разрешает тот, кто тему собирает; granum получает полные данные.
- Приложение выбирает **одну** тему на сборке (`theme`); данные остальных не читаются. Режимы —
  открытый набор, главный `light`; режим может наследовать режим той же темы (`modes.define` с
  `extends` — бывшие темы приложения).
- Активация — атрибут на корне, по умолчанию `data-theme="<тема>-<режим>"`: атрибут каноничен, а одно
  значение несёт и тему, и режим — остров режима и превью другой темы выражаются одним атрибутом.
- Токены компонентов по темам лежат у компонента (`themesDir`) и материализуются в манифест на сборке
  провайдера. Компонент может нести токены для темы чужого каталога: владелец тем — отдельный пакет
  без компонентов, а пакеты компонентов — его потребители.

Вариант 1 отвергнут: каталог и наследование держались бы на соглашении об именах, полнота — на
дисциплине. Вариант 2 отвергнут: селекторы в файлах — источник описанного расхождения `.dark`, и
читать пришлось бы все файлы. Отдельный атрибут режима (`data-mode`) рядом с атрибутом темы отвергнут:
два атрибута расходятся на островах и в телепортах, канон `data-theme` теряется без выигрыша.

Рантайм-переключение тем не требуется сейчас. Задел — превью-темы (`previews`): полные блоки пар без
выхода под `:root`.

**Следствия.** Мажор 3.0: контракт провайдера 2, манифест 3, конфиг `theme` + `previews` + `modes`,
контроллер переключает режим; манифест формата 2 у провайдера без тем читается. Требования — §5.3,
§10.4, §11, §18.4 [`spec.md`](./spec.md); инварианты тем и режимов заменяют INV-THM-* вместе с
тестами. Пересмотр — до заморозки контракта на первом предрелизе 3.0.

## ADR-12. Темы сборки: одна основная, остальные — своими листами

**Контекст.** В 3.0–3.7 тема сборки одна (`theme`), остальные показываются превью (`previews`):
полные блоки пар без выхода под `:root`, с 3.6 — отдельным листом (`css.previews: 'separate'`). Одно
понятие — какие темы есть в сборке — разложено на три ключа с разными правами: у превью собираются
все режимы без выбора, у них нет `define` и `tokenOverrides`, их лист — виртуальный модуль без
адреса, и поставить превью-тему на корень рантайм не умеет. При этом блоки превью уже полные и
годятся для корня: ADR-11 оставил их заделом на рантайм-переключение тем. Потребность появилась:
приложению дизайн-системы нужно показывать каталог тем целиком — основы, контролы, ассеты темы, — а
приложению нескольких брендов — выбирать тему на старте.

**Варианты.**
1. Оставить `theme` + `previews` и научить рантайм ставить превью на корень.
2. Сборка на тему: N сборок приложения, переключение — переход между ними.
3. Список тем сборки: одна основная — в общем листе и под `:root`, остальные — каждая своим листом с
   адресом в манифесте; режимы у каждой свои; рантайм переключает тему и режим.

**Решение.** Вариант 3.

- `themes` — список тем сборки. Запись — тема (id каталога или объект приложения) или
  `{ theme, default?, modes? }`. Основная ровно одна: `default: true`, у единственной темы — без
  пометки. Без `themes` — `defaultTheme` владельца каталога.
- Режимы — у каждой темы свои (`modes`: имена или `{ names, define, tokenOverrides, strictTokens }`),
  правило набора общее: явный список, иначе режим по умолчанию темы и её `define`. Активация общая
  (`activation`: атрибут, шаблон пары, `system`): корень у документа один, и пары всех тем и режимов
  различны.
- Основная тема — в общем листе, как прежняя активная. Дополнительная — свой лист: полные блоки пар,
  никогда `:root`, самодостаточный — общий лист и он дают тему целиком. Манифест импортирует лист
  `?url`: Vite прогоняет его через тот же CSS-конвейер, что общий лист, выпускает ассетом с хешем и
  подставляет адрес (`href`). Готовую строку ассетом не выпускаем — она миновала бы минификацию и
  преобразования lightningcss, и лист темы расходился бы с общим. Страница, которая показывает тему
  всегда, импортирует лист модулем `virtual:granum/themes/<id>.css`.
- Рантайм: состояние — пара «тема + режим». `setTheme` сначала загружает лист темы, потом ставит
  пару; скрипт до первого кадра вставляет `<link>` листа; пары темы без листа не ставит никто.
- `previews` и `css.previews` удаляются без переходного периода: потребители granum 3 — пакеты и
  приложения владельца, и все переводятся одновременно. Минор 3.8 вместо мажора — решение владельца.

Вариант 1 отвергнут: превью остались бы темой второго сорта — без выбора режимов и без своих
значений, — а рантайму пришлось бы различать «превью на корне» и «тему». Вариант 2 отвергнут: цена
сборки растёт в N раз, переключение теряет состояние приложения, а приложению дизайн-системы и
бренда нужен один бандл.

**Следствия.** Манифест рантайма меняет форму: `themes[]` с режимами, адресом листа и `extensions`
каждой темы, `defaultTheme`, общая `activation`. Ядро дизайн-системы читает новую форму и поднимает
peer до `>=3.8`. Модули `virtual:granum/previews*` удалены, их место заняли
`virtual:granum/themes/<id>.css` и `virtual:granum/themes.css`. Положение ADR-11 «приложение
выбирает одну тему» читается теперь как «одну основную». Требования — §10.1, §10.3, §10.4, §11
[`spec.md`](./spec.md). Пересмотр — до следующего мажора.

## ADR-13. Значения компонентов — у темы; версия, целевые пакеты, наследование и копия

**Контекст.** В 3.0–3.9 значения токенов компонента по темам лежат у компонента (`themesDir`,
C-33): тема — данные владельца каталога, а вид компонента под ней — файлы пакета компонентов.
Отсюда четыре следствия.

- Новая тема для пакета компонентов — правка самого пакета. Тема, которая выпускается отдельно
  или живёт в приложении, задаёт значения компонентам только плоскими токенами темы-объекта
  (A-27) — вслепую: есть ли у компонента такой токен, никто не проверяет.
- Тема не говорит, под какие версии компонентов написана. Пакет вырос, тема отстала — это видно
  только по `theme-incomplete`, и то если токен читается без запасного значения.
- C-37 советовал общее для всех тем значение класть запасным в `var(--x, …)`. Значение темы
  пряталось в CSS компонента, полнота (C-30, D-12) его не считала, и тема, которая его не задала,
  молча получала чужое.
- Начать тему можно было только наследованием (`extends`) — живой связью, при которой правка
  родителя приходит в потомка. Независимой темы, которая начинается с копии, контракт не знал, а у
  темы-объекта `extends` давал только токены компонентов: данные обязаны были быть полными.

Потребность: дизайн-системе нужны темы, которые ведут разные авторы и выпускают разные пакеты, с
проверяемой совместимостью — и без правки пакета компонентов.

**Варианты.**
1. Оставить значения у компонентов и добавить теме `targets`.
2. Значения у темы: раздел `components` по пакетам и компонентам; `version` и `targets`; исходник
   темы папкой; копия командой; у темы-объекта — живое наследование. Внешняя тема подключается
   объектом.
3. Тема — отдельный вид пакета-провайдера, второй владелец каталога: снять A-23.

**Решение.** Вариант 2.

- Имена токенов — контракт пакета компонентов, значения — тема. Раздел
  `components.<providerId>.<Name>` данных темы; принадлежность сверяется по манифестам графа:
  токен раздела обязан быть требованием компонента извне, а хук, присваиваемое компонентом и
  чужое — находка. У значения в данных темы один владелец.
- Версия и целевые пакеты: диапазон semver на пакет; выход — предупреждение сборки и находка.
  Версия — грубый сигнал, полнота (D-12) — точный: нужны оба.
- Наследование и копия законны оба и различаются явно. Наследование — живая связь, раскрывается
  на каждой сборке того, кто тему собирает: новый токен родителя потомок получает молча. Копия —
  независимая тема, раскрытая один раз командой: новый токен источника она получает находкой
  `theme-incomplete`, и решение за автором. Наследование режимов внутри темы остаётся как было:
  это связь внутри одной темы.
- Тема-объект с `extends` дополняется из родителя: внешний пакет темы наследует живьём от
  установленной темы каталога. Унаследованное идёт слоем данных родителя, собственные отличия —
  слоем приложения: наследник без отличий выглядит как родитель. `targets` при наследовании
  сливаются по пакету.
- Хук — ручка приложения, тема его не задаёт: значение, которое даёт тема, делает токен токеном
  темы. Значение темы в `var(--x, …)` компонента не прячется.
- `themesDir` остаётся (контракт заморожен до мажора) — для значений компонента под чужую тему
  (C-35). Если один токен в одном режиме задают и тема, и компонент, — `token-conflict`.
- Владелец каталога в графе по-прежнему один (A-23): внешняя тема подключается объектом.

Вариант 1 отвергнут: новая тема по-прежнему правит пакет компонентов, а внешняя тема и тема
приложения задают значения компонентам вслепую. Вариант 3 отвергнут сейчас: второй владелец
каталога — второй реестр, и правила их слияния — отдельное решение, а тема-объект закрывает
потребность без него. Пересмотр — когда у дизайн-системы станет больше одного внешнего пакета тем и
подключение объектом станет неудобным.

**Следствия.** Данные темы и индекс каталога получают `version`, `targets` и раздел `components`;
каталог провайдера принимает исходник темы; `dist` несёт значения раздела ещё и слитыми, поэтому
читатель до 3.10 даёт тот же CSS. Новые коды — `theme-target-mismatch`, `theme-component-unknown`,
`theme-token-foreign`; команда `granum theme copy`. Поведение темы-объекта с `extends` меняется:
данные дополняются из родителя. C-37 и C-39 переписаны. Контракт провайдера (версия 2) и формат
манифеста (версия 3) не меняются — минор 3.10. Требования — §3, §5.3, §10.1, §10.4, §12, §14,
§18.6 [`spec.md`](./spec.md); работы — этап 10 [`plan.md`](./plan.md).
