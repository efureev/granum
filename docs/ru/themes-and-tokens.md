# Темы и токены

> 🇬🇧 English version: [`../en/themes-and-tokens.md`](../en/themes-and-tokens.md).

Токен — CSS custom property (`--th-accent`). **Тема** — дизайн-язык: полный набор
значений токенов без селекторов, режимонезависимые (`root`) и по **режимам**
(`light`, `dark`, дальше любые). Темы сборки перечисляет приложение: одна
**основная** — в общем листе и под `:root`, остальные **дополнительные** — каждая
своим листом. Тема и режим включаются парой в атрибуте корня и переключаются в
рантайме. Все имена в данных, конфигах и файлах токенов пишутся **без** `--`:
префикс добавляет генератор, а ключ с `--` — ошибка (`InvalidTokenKeyError` у
провайдера, `InvalidConfigError` с путём до поля у приложения).

## Тема, режим, пара

| Понятие | Что это |
|---|---|
| тема | `GranumThemeData`: `id` (slug `^[a-z][a-z0-9-]*$`), `title`, `root`, `modes`, `defaultMode` (по умолчанию `light`), `baseCss`, `extensions` |
| режим | значения режимозависимых токенов: `{ colorScheme, tokens, extends?, title?, fallbacks? }`; имя — slug без дефиса, `root` запрещено |
| пара | значение атрибута активации: `<тема>-<режим>` (`slate-light`, `ink-dim`) |
| каталог | темы, которые объявляет провайдер; владелец каталога в графе — один |
| реестр | словарь владельца: токен → `root` или `mode`; по нему сборка проверяет полноту темы |
| основная тема | тема сборки под `:root`: её блоки — в общем листе, её режим по умолчанию действует без атрибута |
| дополнительная тема | тема сборки своим листом: полные блоки пар, никогда под `:root` |

`extends` режима ссылается на режим той же темы: итоговые токены — предки по
цепочке, затем свои. `extensions` granum не интерпретирует: поле уезжает в
`virtual:granum/themes` как есть — так дизайн-система передаёт приложению,
например, пропы компонентов по умолчанию.

## Темы сборки

Каталог объявляет провайдер — обычно отдельный пакет токенов без компонентов
([авторам провайдеров](./authoring-providers.md#темы-каталог-реестр-данные)).
Приложение перечисляет темы сборки в `themes`:

```ts
export default defineGranumConfig({
  engine: windEngine(),
  providers: ['@acme/ui'],
  themes: [
    { theme: 'ink', default: true, modes: ['light', 'dark', 'dim'] }, // основная
    { theme: 'paper', modes: ['light', 'dark'] },                     // дополнительная
    '@acme/tokens:clay',                                              // квалифицированный id, только режим по умолчанию
  ],
})
```

Запись — тема (id каталога, `'@acme/tokens:ink'` или тема-объект приложения) или
`{ theme, default?, modes? }`. Основная тема ровно одна: у списка из одной записи —
она, у нескольких — помеченная `default: true`; ни одной пометки или две —
`InvalidConfigError('themes')`. Пустой список — тоже ошибка: сборка без тем — это
граф без владельца каталога. Без `themes` берётся `defaultTheme` владельца каталога
(или единственная тема каталога). Порядок записей — порядок тем в манифесте.

Источник основной темы виден в отчёте и `doctor` как `themeSource`: `provider` —
id из конфига, `default` — тема по умолчанию владельца, `app` — тема-объект
приложения. Владельца не обязательно перечислять в `providers`: строковая
зависимость манифеста (`dependencies: ['@acme/tokens']`) подгружает донора от
каталога зависящего пакета, и его компоненты селекция `'all'` не выбирает.

Данные читаются только у тем из `themes`; остальные темы каталога в сборку не
попадают и не открываются. Неизвестный id — `ThemeResolutionError`
(`unknown-theme`) со списком доступных; одна тема дважды — `duplicate-theme`; два
владельца каталога в графе — `multiple-theme-owners`.

## Набор режимов и режимы приложения

Режимы — у каждой темы свои, в `modes` её записи: массив имён или объект
`{ names, define, tokenOverrides, strictTokens }`. Без `names` в CSS едут режим по
умолчанию темы (`light`) и ключи её `define`: тема собирается под приложение, и
второй режим — его решение, а не умолчание. Правило одно для основной и
дополнительной темы. Режим по умолчанию всегда первый; если `names` его не
называет, режимом по умолчанию темы в сборке становится первый из набора. Режим,
от которого наследует режим набора (`extends`), сам в набор входить не обязан: его
значения берутся по цепочке, блока у него нет. Имя вне темы и её `define` —
`unknown-mode`.

```ts
themes: [{
  theme: 'ink',
  modes: {
    names: ['light', 'dark'],
    define: {
      ocean: { extends: 'dark', tokens: { 'th-accent': '#0ea5e9' }, title: 'Океан', colorScheme: 'dark' },
      sepia: { extends: 'light', tokensRef: new URL('./src/sepia.css', import.meta.url).href },
    },
    tokenOverrides: { root: { 'th-radius': '4px' }, dark: { 'th-bg': '#050505' } },
    strictTokens: true,
  },
}]
```

`define` — режим приложения поверх режима своей темы или другого её `define`: берёт
итоговые значения базы (с токенами компонентов) и дописывает свои. Фолбэки
`@supports` база отдаёт посчитанными от своих значений; режиму, который меняет
роли, нужны свои — `fallbacks: [{ supports, tokens }]`, они встают после
унаследованных и перекрывают их по токену. Неизвестная
база и цикл — предупреждения `mode-extends-unresolved` и `mode-extends-cycle`,
такой режим наследует режим по умолчанию. Имя `define`, совпавшее с режимом своей
темы, — та же пара, ошибка `activation-collision`. `tokensRef` — CSS-файл
приложения с одним плоским блоком токенов; литеральные `tokens` важнее. Файл с
несколькими блоками — ошибка `multiple-blocks`, если нужный блок не назван в
`selector`.

`tokenOverrides.root` ложится в режимонезависимые значения своей темы,
`tokenOverrides.<режим>` — в её режим; режим вне набора — `unknown-mode`. При
`strictTokens: true` override токена, которого нет ни в данных темы, ни в токенах
компонентов, отбрасывается, а в отчёт попадает `override-skipped`. Значения одной
темы не трогают другую.

## Активация

Тема и режим включаются атрибутом на корне: по умолчанию
`data-theme="<тема>-<режим>"`. Атрибут, шаблон значения и системная схема — общие
на все темы сборки, в `activation`: корень у документа один.

```ts
activation: { attribute: 'data-theme', value: '{theme}-{mode}', system: 'media' }
```

Шаблон обязан содержать `{mode}`, а значения всех пар всех тем сборки и их
`define` — различаться; иначе `activation-collision`. `system: 'media'` добавляет
тёмный режим основной темы по `prefers-color-scheme` для страницы, на которой
атрибут ещё не выставлен: корень без атрибута — всегда основная тема. Классов
`.light`/`.dark` granum не выводит. Вариант `dark:` движка строится по парам с
`colorScheme: 'dark'` **всех** тем сборки (`[data-theme="ink-dark"] .dark\:…`):
утилиты живут в общем листе, а тёмной бывает и пара дополнительной темы. Это
потомковый селектор, и светлый остров внутри тёмной страницы его тоже совпадает —
для островов служат токены режима, а не вариант.

## Слои значений

Значение токена темы сборки в режиме собирается из слоёв, каждый следующий
перекрывает:

1. данные темы — `root`, затем цепочка режима;
2. токены компонентов для этой темы — в порядке селекции;
3. тема-объект приложения;
4. `modes.define` записи темы;
5. `modes.tokenOverrides` записи темы.

Токен, объявленный хоть в одном режиме, получает значение в каждом: по цепочке
`extends` режима, иначе из режима по умолчанию. Такое значение — запасное: то,
что режиму уже дал другой слой, оно не перекрывает. Значение, взятое из режима по
умолчанию, приходит с его фолбэками `@supports` для этого токена — раньше своих
фолбэков режима. Одна функция считает значение
для CSS, отчёта и CLI: `granum tokens <id:Name> --deep` показывает цепочку слоёв по
каждому режиму основной темы вместе с темой и режимом, откуда пришло значение.

## Токены компонента по темам

Токены компонента лежат у компонента, в папке `themesDir`: `<тема>/root.json` и
`<тема>/modes/<режим>.json` (или `.css` с одним плоским блоком). Сборка провайдера
кладёт их в манифест. Для каждой темы сборки значение токена ищется так: режим, его
предки по `extends`, режим по умолчанию — и в каждом из них сначала тема, затем её
предки по каталогу. Так у темы `ink`, наследующей `paper`, режим `dim`
(наследует `dark`) берёт токен кнопки из `paper/modes/dark.json`, если у `ink` его нет.
Цепочка у каждой темы своя: дополнительная тема не берёт токенов у основной, если
та не её предок.

Компонент вправе класть токены для тем чужого каталога — спутник для темы
дизайн-системы: они применяются, когда эта тема есть в сборке. Папка темы, которой
нет ни в одном каталоге графа, — предупреждение `component-theme-unknown`, а не ошибка.

## Раскладка CSS

```css
/* общий лист — основная тема ink */
@layer granum.tokens {
  :root:not([data-theme]), [data-theme="ink-light"], [data-theme="ink-dark"], [data-theme="ink-dim"] { --th-radius: 2px; }  /* литералы root */
}
@layer granum.themes {
  :where(:root), [data-theme="ink-light"], [data-theme="ink-dark"], [data-theme="ink-dim"] { --th-ring: 0 0 0 2px var(--th-accent); }
  :where(:root), [data-theme="ink-light"] { color-scheme: light; --th-bg: #ffffff; }
  [data-theme="ink-dark"] { color-scheme: dark; --th-bg: #0f172a; }
  [data-theme="ink-dim"] { color-scheme: dark; --th-bg: #1e293b; }
  @supports not (color: color-mix(in oklab, red, red)) {
    :root:not([data-theme]), [data-theme="ink-light"] { … }
  }
}
/* лист дополнительной темы paper */
@layer granum.tokens, granum.base, granum.themes, granum.components, granum.utilities;
@layer granum.themes {
  [data-theme="paper-light"], [data-theme="paper-dark"] { … }  /* формулы */
  [data-theme="paper-light"] { … }                              /* полный блок */
}
```

Формула со ссылкой `var(` — в `root` или одинаковая во всех режимах — стоит под
общей границей основной темы — `:where(:root)` и список её пар: она пересчитывается
на каждом острове режима, а не наследуется готовой от корня. Граница — именно
список пар, а не `[data-theme]`: пару другой темы она не достаёт. Режим по
умолчанию идёт первым под `:where(:root)` и своей парой, остальные — по порядку
набора. `:root` основной темы стоит под `:where()` и весит ноль: пара любого режима
и любой темы на корне перекрывает его специфичностью, а не позицией, — поэтому
каскад не зависит от порядка листов в документе. Затем фолбэки `@supports` в том же
порядке: фолбэк режима по умолчанию — под `:root:not([data-theme])` и своей парой,
иначе он достал бы корень с другой парой. При `system: 'media'` список замыкает
блок `prefers-color-scheme`, и фолбэки тёмного режима лежат внутри того же
медиазапроса. `colorScheme` режима — объявление `color-scheme` в его блоке.
`baseCss` основной темы уходит в слой `base` общего листа.

## Дополнительные темы

Каждая тема сборки, кроме основной, — дополнительная. Каждая её пара получает
полный блок: свои литералы `root`, режим, токены компонентов селекции и фолбэки;
формулы — один раз под списком её пар (`[data-theme="paper-light"],
[data-theme="paper-dark"]`). Префикс значения совпал бы и с парами другой темы
(`slate-` — с `slate-hc-light`). Под `:root` дополнительная тема не выходит
никогда, и обрезка токенов режет её так же, как основную.

Блоков дополнительной темы в общем листе нет — они только в её листе. Лист
самодостаточен: общий лист и он один дают тему целиком, без листов других тем. Он
начинается объявлением порядка слоёв и кладёт блоки в слой `themes`, а свой
`baseCss` — в слой `base` (кроме записей, которые уже есть в общем листе),
поэтому подключённый раньше общего он каскад не меняет. Лист, однажды загруженный,
остаётся в документе, и его `base` действует на всю страницу — в `baseCss`
дополнительной темы место только `@font-face`, `@property` и `@keyframes`; правило
стиля там `doctor` называет находкой `theme-base-global`. Лист приходит двумя путями:

- модулем — страница, которая показывает тему всегда, импортирует его статически:

```ts
// src/pages/themes/[slug].astro — и больше нигде
import 'virtual:granum/themes/paper.css' // одна тема; 'virtual:granum/themes.css' — все дополнительные
```

- адресом из манифеста — для переключения в рантайме: модуль манифеста
  импортирует лист `?url` как файл `/@granum-theme/granum-theme-<id>.css`. На
  сборке Vite прогоняет его через тот же CSS-конвейер, что общий лист, выпускает
  ассетом с хешем и подставляет адрес с учётом `base` в `href` записи темы; в dev
  этот адрес отдаёт dev-сервер. `<link>` в HTML плагин не ставит — лист грузит
  рантайм.

Способы совместимы: лист заканчивается меткой `@property --granum-sheet-<id>` —
вне слоёв и без селектора, — и загрузчик узнаёт лист, уже импортированный
статически, и второй `<link>` не ставит: страница скачивает его один раз.

Модуль основной темы — ошибка с подсказкой, что её блоки в `virtual:granum.css`;
тема не из сборки — ошибка с перечнем дополнительных тем.

Стенд — `apps/app-theme-sheets`: две страницы, лист дополнительной темы модулем
получает только одна, а манифест несёт адрес ассета.

## Своя тема приложения

Запись `themes` принимает и объект `GranumThemeData` — полные данные. Наследование
от темы каталога приложение разрешает само, до конфига, а `extends` говорит
granum, чьи токены компонентов брать за основу:

```ts
themes: [{
  theme: {
    ...brandData,          // полные данные: id, title, root, modes
    extends: 'paper',      // токены компонентов для режимов, где тема их не задала
    sources: ['src/theme'],
  },
}]
```

`extends`, которого нет в каталоге, — ошибка `unknown-theme` со списком доступных:
иначе токены компонентов этой цепочки молча не применились бы.

Тема-объект идёт слоем после токенов компонентов: значение токена кнопки в её
режиме перекрывает токен компонента. `sources` — файлы, из которых тема собрана:
конфиг читается один раз на процесс Vite, поэтому их правка в dev перезапускает
сервер. Стенд — `apps/app-theme-own`.

## Потребление и отчёт

Сборка провайдера записывает в манифест, какие токены компонент
**потребляет** (`var(--x)` в CSS и JS, литералы `'--x'` в JS, `dynamicTokens`)
и какие из них **требует извне**: потребление без fallback минус то, что
компонент присваивает сам (`--x:` в своём CSS, переменные `v-bind()` из
`<style>`). Приложение объединяет потребление с `appSources` — это корни
обрезки. `token-undefined` в отчёте и в `doctor` — одно множество: токен,
который выбранный компонент требует извне (кроме `dynamicTokens`) и который не
получил значения ни в одном режиме ни одной темы сборки и не объявлен инлайнимыми
файлами. Токены разметки самого приложения в него не входят.

Токен, который компонент читает **только** через `var(--x, запасное)`, извне не
требуется, но и молчать о нём опасно: если его не задаёт ни один слой, компонент
всегда рисует запасное значение, и переименованный токен этим и прячется. Сборка
записывает такие токены в манифест отдельно, а `doctor` называет незаданные
находкой `token-fallback-only`. Намеренный хук — значение по умолчанию, которое
тема или приложение вправе переопределить, — компонент объявляет в `hookTokens`.

## Обрезка токенов

```ts
pruneTokens: { mode: 'on', keep: ['th-brand-*'] }
```

Обрезка удаляет из слоёв `tokens` и `themes` объявления, недостижимые от
корней; `base` не трогается. Данные тем и токены компонентов — пакетный слой и
режутся по достижимости у каждой темы сборки. Корни: потребление в CSS компонентов
селекции и в выводе движка, `consumes` и `dynamic` из манифестов, `appSources`,
значения приложения (`define` и `tokenOverrides` записей тем, темы-объекты), `keep`.
Достижимость идёт по графу «токен → токены в его значении», поэтому
`--soft: color-mix(…, var(--danger))` держит `--danger`. Токен, нужный одному
режиму, сохраняется во всех.

Порядок внедрения: `mode: 'report'` → посмотреть план в отчёте или
`granum prune` → `mode: 'on'`. Режим `off` не меняет эмиссию ни на байт.
Стенд [`bench-pruned`](./measuring-weight.md) показывает эффект.

## Рантайм

```ts
import { createThemeController } from '@feugene/granum/runtime'
import manifest from 'virtual:granum/themes'

const themes = createThemeController(manifest)
themes.themes()            // [{ id: 'ink', modes, defaultMode }, { id: 'paper', …, href: '/assets/granum-theme-paper-….css' }]
themes.theme.id            // 'ink'
themes.modes()             // режимы текущей темы: [{ name: 'light', value: 'ink-light', colorScheme: 'light' }, …]
themes.setMode('dim')      // <html data-theme="ink-dim">
await themes.setTheme('paper') // лист paper, затем <html data-theme="paper-dark">
themes.subscribe(({ theme, mode }) => {})
```

Манифест — темы сборки в порядке конфига (у каждой режимы с парами в порядке CSS,
режим по умолчанию, `href` листа у дополнительной и `extensions`), `defaultTheme`
и атрибут активации; кроме адресов листов, от селекции компонентов он не зависит.
`setTheme` сначала загружает лист темы (`loadThemeSheet`) и только потом ставит
пару: значения темы без листа были бы чужими. Пока грузится лист дополнительной
темы, выбранной на старте, `setMode` пару тоже не ставит — лишь запоминает режим;
не загрузился лист — контроллер остаётся в основной теме. Исход загрузки ссылки,
вставленной ранним скриптом, отмечен на ней (`data-granum-state`), поэтому упавший
до контроллера лист не ждётся вечно, а следующий `setTheme` грузит его заново.
Режим при смене темы — заданный
`mode`, иначе одноимённый текущему, иначе первый той же схемы, иначе режим по
умолчанию темы.

Контроллер хранит не пару, а ключ выбора (ключ `granum-theme`): у основной темы —
имя режима, у дополнительной — `<тема>-<режим>` (`themeSelectionKey`). Режим
основной темы без её имени переживает смену основной темы на сборке; ключ,
который не называет режим выбираемой темы сборки, выбора не даёт. На старте
`initial: 'auto'` берёт пару, уже выставленную на корне, — тогда корень не
трогается, а лист её темы контроллер находит и ждёт; иначе сохранённый выбор,
системную схему (первый режим основной темы с подходящим `colorScheme`) и режим
по умолчанию. Сохранённая дополнительная тема ставится после загрузки листа —
`ready`; лист не загрузился — контроллер остаётся в основной теме. `initial`
может и назвать выбор явно — режим основной темы или `{ theme?, mode? }`, ту же
форму, что у `themeRootAttributes`: сервер, прочитавший выбор из cookie, отдаёт
его же приложению, которое рендерит.

Пару до первого кадра ставит `createThemeScript` или опция плагина
`themeScript` ([серверный рендер](./ssr.md)): для дополнительной темы скрипт
сначала вставляет `<link rel="stylesheet" blocking="render">` её листа, а тему без
адреса листа (манифест, собранный до сборки) не выбирает.
