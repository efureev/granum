# Использование в приложениях

> 🇬🇧 English version: [`../en/usage-in-apps.md`](../en/usage-in-apps.md).

Приложение описывает, **какие** компоненты и темы ему нужны, в
`granum.config.ts`; плагин `granum()` строит из манифестов провайдеров одну
резолюцию и кормит ею три канала: CSS, JS и темы.

## Конфиг

```ts
import { defineGranumConfig } from '@feugene/granum/vite'
import { windEngine } from '@feugene/granum-engine-wind'

export default defineGranumConfig({
  engine: windEngine(),
  providers: ['@acme/ui', '@acme/base'],
  components: [{ provider: '@acme/ui', names: ['XhPanel'] }, '@acme/base:XBox'],
  themes: { names: ['light', 'dark'], tokenOverrides: { light: { 'xh-accent': '#0a7' } }, strictTokens: true },
  appSources: { dirs: ['src'] },
  css: { layers: true, layerPrefix: 'granum' },
  js: { guard: 'error' },
  pruneTokens: { mode: 'off' },
  report: { file: 'granum-report.json' },
})
```

| Поле | Значение по умолчанию | Смысл |
|---|---|---|
| `engine` | — (обязательно) | инстанс движка утилит: `windEngine()` из `@feugene/granum-engine-wind` или свой; строка `'builtin'` и объект опций не принимаются |
| `providers` | — | имена пакетов (манифест ищется через `exports["./granum.manifest.json"]`) или объекты контракта; объект с `baseUrl` на существующий `dist` сканируется приложением само (медленный путь, `provider-scanned`). Порядок в слоях задаёт граф `dependencies` провайдеров: донор раньше зависящего; независимые провайдеры идут в порядке списка |
| `components` | `'all'` | список ключей `id:Name` / `{ provider, names }` либо `'imports'` — по импортам в `appSources` |
| `themes.names` | по `define` → `defaultThemes` провайдеров → `['light']` | активный набор тем |
| `themes.define` | — | темы приложения: `{ extends, tokens, tokensRef, label, colorScheme }` |
| `themes.tokenOverrides` | — | значения поверх всех слоёв провайдеров |
| `themes.strictTokens` | `false` | override токена, который не объявлен ни одним слоем, отбрасывается |
| `appSources` | — | директории, из которых извлекаются классы и потребление токенов приложения. Без него классы разметки приложения CSS не получают, и сборка предупреждает; `{ dirs: [] }` — явно «своих классов нет» |
| `css.layers` | `true` | обёртки `@layer`; `false` — плоская конкатенация в том же порядке |
| `js.guard` | `'error'` | импорт компонента вне селекции: ошибка, предупреждение или ничего |
| `js.dts` | — | куда писать объявления для `virtual:granum/components`, например `src/granum.d.ts` |
| `pruneTokens.mode` | `'off'` | `'report'` — план в отчёте, `'on'` — обрезка слоёв `tokens` и `themes` |
| `report.file` | `'granum-report.json'` | отчёт сборки в `outDir`; `false` — не писать |
| `report.brotli` | `false` | считать ли размеры слоёв в brotli: качество 11 — 151 мс на 222 kB против 2 мс у gzip |

Форма конфига проверяется при загрузке: `InvalidConfigError` называет путь до
поля. Неизвестный ключ — тоже ошибка: для опечатки она предложит ближайший ключ
(`appSource` → `appSources`), для ключа пресета v1 — скажет, куда он делся.
`defineGranumConfig` ловит лишний ключ ещё в редакторе. Один и тот же объект
конфига читают CLI и плагин, поэтому `doctor` видит ровно ту селекцию, что уйдёт
в сборку.

## Селекция

Список компонентов замыкается транзитивно по `dependencies` из манифестов:
зависимости встают раньше зависящих (post-order DFS), и этот порядок
нормативен для CSS и токенов. `components: 'imports'` вычисляет стартовый
список по импортам вида `@acme/ui/components/XhPanel` и по PascalCase-тегам в
`appSources`. Берутся только компоненты провайдеров графа: `~/components/…`
приложения и `components/` чужих пакетов селекцию не трогают, закомментированный
импорт тоже.

Рекомендуемый режим — явный список: он держит селекцию в одном месте, где её
видно на ревью. `'imports'` уместен там, где набор компонентов часто меняется,
но помните про его границу: компонент, отрисованный по вычисленному имени
(`<component :is="name">`), скан не находит, и его CSS в сборку не попадёт.

Guard в `resolveId` ловит импорт компонента, которого нет в селекции, и
называет импортёра:

```
[granum] ComponentOutsideSelectionError: '@acme/ui:XhTable' is imported by
src/App.vue but is not part of the selection [@acme/ui:XhPanel, …]
```

Составной компонент отдаёт части своим модулем: `XhListItem` живёт в `XhList`, а
подпуть `@acme/ui/components/XhListItem` — алиас `exports` на модуль владельца
(`granum codegen --subcomponents`). Сборка провайдера записывает такие части в
манифест владельца, и приложение судит по части владельца: подпуть части при
селекции без `XhList` — `ComponentOutsideSelectionError` на `XhList` с названной
частью, в режиме `'imports'` импорт или тег `<XhListItem>` добавляют в селекцию
`XhList`, а часть из корня пакета — та же ошибка, что и компонент. Провайдер,
собранный прежней версией granum, частей в манифесте не несёт — пересоберите его.

## Движок и классы пакетов

`engine` в конфиге — инстанс движка утилит: своего у granum нет, выбор делает
приложение. Правила приложения передаются фабрике движка
(`windEngine({ rules: […] })`), у конфига поля для правил нет.

Списку классов в манифесте granum верит только при равенстве отпечатков
словаря: в блоке `engine` манифеста записан отпечаток той реализации, которая
список отфильтровала. При различии классы пакета пересчитываются движком
приложения из файлов манифеста, и разница называется — `gained` (сборка пакета
потеряла, приложение вернуло) и `lost` (правила нет у приложения; класс
остаётся во входе движка и виден в `unmatched`). Модуль правил пакета грузится
по равенству диалектов, а не отпечатков; полностью таблица решений — в
[движках и диалектах](./engines-and-dialects.md).

## CSS-канал

```ts
import 'virtual:granum.css'
```

Модуль содержит объявление порядка и пять слоёв:

```css
@layer granum.tokens, granum.base, granum.themes, granum.components, granum.utilities;
@layer granum.tokens { … }      /* theme.tokensCss провайдеров, структурные токены :root */
@layer granum.base { … }        /* preflight движка, затем theme.baseCss */
@layer granum.themes { … }      /* блоки токенов активных тем, файлы тем */
@layer granum.components { … }  /* cssFiles и styles.css компонентов селекции */
@layer granum.utilities { … }   /* утилиты движка */
```

Вход движка — объединение статических классов компонентов селекции (из
манифестов), их safelist и классов, извлечённых из `appSources`. Один слой
отдельно: `virtual:granum/layers/utilities.css` — со своей обёрткой `@layer`;
конкатенация слоёв равна целому. Нелейерный CSS приложения перебивает всё, что
внутри слоёв, — так и задумано: утилита в шаблоне приложения побеждает базовый
стиль компонента.

У этого правила есть оборотная сторона, на которую легко наступить:
**сброс браузерных стилей — тоже нелейерный CSS**. Импортированный как есть,
он побеждает утилиты и CSS компонентов независимо от специфичности: правило
`button { color: inherit }` из типового reset сильнее класса `.text-[var(--…)]` в
`@layer granum.utilities`. На витрине дизайн-системы это дало красную кнопку с
тёмным текстом и контраст 2.89:1 вместо 4.5:1.

Лечится одной строкой — сброс импортируется в свой слой:

```css
/* src/styles/reset.css — импортируется ПЕРЕД virtual:granum.css */
@import '@unocss/reset/tailwind-compat.css' layer(reset);
```

Место слоя в каскаде задаёт первое его появление, поэтому сброс, импортированный
раньше, проигрывает всем слоям granum — как и положено сбросу.

С пресетом v1 этого вопроса не было: там «слои» UnoCSS — порядок вывода, а не
каскадные слои, и спор решался специфичностью, где класс сильнее тега.

### Отдельный ассет на слой: `css.split`

Один файл жмётся лучше, но инвалидируется целиком: правка разметки сбрасывает
кеш токенов и тем, которые не менялись.

```ts
export default defineGranumConfig({
  engine: windEngine(),
  providers: ['@acme/ui'],
  appSources: { dirs: ['src'] },
  css: { split: true },
})
```

Каждый непустой слой уезжает своим ассетом с собственным хешем, а `<link>` на
них проставляются в HTML в порядке слоёв — порядок ссылок и есть порядок
каскада. Правка разметки после этого меняет один ассет из пяти; остальные
четыре браузер берёт из кеша. Стенд `apps/bench-split` проверяет именно это:
две сборки и сравнение имён. Ассет слоя проходит CSS-конвейер Vite, как любой
CSS сборки: PostCSS из конфига, минификацию и `build.cssTarget`.

Границы опции: она действует только на сборке приложения и только там, где есть
HTML-точка входа — ссылки проставляются в неё, и без HTML плагин скажет об этом
предупреждением. Нужен и `build.cssCodeSplit` (по умолчанию включён): без него
Vite склеивает весь CSS в один файл, и плагин тоже скажет об этом. Серверная сборка HTML не порождает, а в dev хешированных
ассетов нет вовсе, и CSS там по-прежнему приходит одним модулем. Платить
приходится суммарным весом: каждый файл жмётся своим словарём. На витрине
дизайн-системы (8 провайдеров, 226 kB CSS) это 34.5 kB gzip пятью слоями и
ассетом входа против 33.5 kB одним файлом — **+3% на первый визит**. Взамен
правка разметки перекачивает 21.2 kB вместо 33.5, правка темы — 2.5 kB. На
маленьком CSS доля накладных выше: стенд `apps/bench-split` — 3.0 kB против
2.5 kB (+18%). Опция окупается там, где повторных визитов много, а фундамент
меняется редко; если страницу читают один раз, плата идёт впустую.

### Хост с несколькими окружениями Vite

Хост вправе собрать несколько окружений Vite одним билдом: Astro строит
`prerender`, `ssr` и `client`, разрешая конфиг каждого до первой сборки и
вызывая финальные хуки на каждое. Резолюция и эмиссия от этого не страдают —
они мемоизированы и происходят один раз. Отчёт считается по CSS всех окружений
и от их порядка не зависит: класс с правилом в CSS клиента не попадает в
`unmatched`, даже если сервер собран раньше. Размеры слоёв берутся с одного
окружения (клиентского, если в его CSS есть слои granum), чтобы копия CSS в
двух окружениях не считалась дважды, а окружение без CSS-ассетов в итог не
входит.

Отчёт пишется в каталог клиентского окружения, а не того, что собрано
последним: у окружения каталог бывает временным (у Astro `prerender` это
`dist/.prerender/`, который хост удаляет после сборки). Окружение, собранное
позже, может изменить итог — тогда отчёт переписывается, а строка сборки
печатается заново; если оно очищает каталог (`emptyOutDir`), отчёт
возвращается на место.

Инстанс `granum()` обслуживает одну сборку со всеми её окружениями. Отдельным
сборкам — например, client и затем SSR в одном скрипте — нужен свой
`granum(config)` на каждую: тот же инстанс во второй сборке отдал бы резолюцию и
CSS первой, поэтому плагин отвергает его ошибкой `PluginInstanceReusedError`.

`css.split` на таком хосте неприменим: `<link>` проставляются через
`transformIndexHtml`, а HTML такой хост строит сам, мимо этого хука. Опцию
надо оставить в умолчании `false` — тогда CSS приезжает одним модулем
`virtual:granum.css`, который хост подхватывает как обычный CSS-импорт.

## JS-канал

```ts
import { XhPanel } from 'virtual:granum/components'
```

Виртуальный модуль реэкспортирует компоненты селекции из их subpath и не
имеет побочных эффектов: tree-shaking вырезает невостребованное. Обычные
импорты `@acme/ui/components/XhPanel` тоже работают; плагин не переписывает
код провайдера и не меняет раскладку чанков.

Компонент берут только так — из подпути или из виртуального модуля. Импорт
компонента из корня пакета (`import { XhPanel } from '@acme/ui'`) и корня целиком
(`import * as ui`, `export * from`, `import()`) guard отвергает ошибкой
`ComponentRootImportError`: селекция видит компонент по подпути, а корень тянет
весь пакет — в dev и в SSR это все его компоненты. Прочие имена корня — утилиты,
константы, типы — импортировать можно. Строгость задаёт тот же `js.guard`.

Реэкспорт по имени возможен не для каждого компонента. `date-picker` не
идентификатор JS, а `Card`, выбранный у двух провайдеров сразу, неоднозначен.
Такие имена модуль пропускает и называет предупреждением сборки — их
импортируют из subpath пакета: `@acme/ui/components/date-picker`.

Важно, что каналы разные: JS идёт по импортам, CSS — по селекции.
Компонент, который есть в селекции, но не импортирован, в бандл не попадёт, а
его CSS попадёт. Чтобы ушло и то и другое, сужайте селекцию, а не импорты.

Типы. Амбиентные объявления виртуальных модулей поставляет сам пакет — ссылка
один раз в любом `.d.ts` проекта:

```ts
/// <reference types="@feugene/granum/client" />
```

Имён компонентов там нет и быть не может: они зависят от селекции
приложения, а не от пакета, и импорт оттуда типизирован как `any`. Точные
объявления порождает плагин — как `components.d.ts` у авто-импорта:

```ts
// granum.config.ts
js: { dts: 'src/granum.d.ts' }
```

Файл переписывается только при смене селекции и его место — в гите:

```ts
declare module 'virtual:granum/components' {
  export { XhPanel } from '@acme/ui/components/XhPanel'
}
```

## Auto-import

Для `unplugin-vue-components` и совместимых инструментов есть резолвер: по
имени компонента он отдаёт subpath провайдера, неизвестное или неоднозначное
имя (два провайдера с одним `Name`) не резолвит. Часть составного компонента
(`<XhListItem>`) резолвится своим подпутём — guard и селекция сводят его к
владельцу; компонент с тем же именем у другого провайдера первичен.

```ts
import { granum, granumResolver } from '@feugene/granum/vite'
import Components from 'unplugin-vue-components/vite'

export default defineConfig({
  plugins: [vue(), granum(config), Components({ resolvers: [granumResolver(config, { prefix: 'Xh' })] })],
})
```

В режиме `components: 'imports'` селекция пополняется не резолвером, а
сканом PascalCase-тегов в `appSources`: `<XhPanel>` без импорта попадает в
селекцию, если имя объявляет ровно один провайдер графа. Так селекция не
зависит от порядка трансформаций бандлера.

## Темы в рантайме

```ts
import { createThemeController } from '@feugene/granum/runtime'
import manifest from 'virtual:granum/themes'

export const themes = createThemeController(manifest)
themes.set('dark')
```

Манифест тем — имена, селекторы и режим активации (`data-theme`, класс,
`:root`), выведенные из той же резолюции. Подробно —
[Темы и токены](./themes-and-tokens.md).

## Dev-режим

Правка исходника приложения перегенерирует слой `utilities` и приезжает по
HMR: модуль, чей код не изменился (например, `virtual:granum/themes`), не
перезагружается, и страница остаётся на месте. Изменение манифеста или CSS
провайдера (монорепо, `vite build --watch` у провайдера) инвалидирует
резолюцию целиком — за файлами провайдера dev-сервер следит сам, даже если
пакет лежит вне корня приложения. Ошибки резолюции показываются оверлеем Vite.

## Отчёт сборки

`dist/granum-report.json` — селекция, темы и их источник, классы без правила
с источниками, safelist-записи, покрытые статикой, план обрезки, токены без
объявления, размеры слоёв raw/gzip/brotli по собранному ассету после
минификации (`sizesSource: 'bundle'`) и по эмиссии (`emissionSizes`).
Прочитать его: `granum report`.

Времени сборки в отчёте нет и не будет: он обязан быть побайтно стабильным
между сборками, а время стабильным не бывает. Оно печатается строкой в
лог сборки:

```
[granum] time 997 ms (prepare 646 [manifests 547, scan 92, resolve 7], emit 335, report 16)
```

`prepare` — подготовка, разложенная на три части: `manifests` — чтение
манифестов и пересчёт классов, `scan` — извлечение классов из исходников
приложения, `resolve` — сама резолюция. Дальше `emit` — генератор утилит и
сборка слоёв, `report` — размеры слоёв и запись файла. Всё остальное в
сборке — vue, бандлер, минификация — не granum.

Большой `manifests` почти всегда значит пересчёт классов: отпечаток
словаря пакета разошёлся с движком приложения — например потому, что
приложение передало движку свои правила, — и классы читаются из файлов
пакета (`granum doctor` назовёт причину). На восьми провайдерах дизайн-системы
это полсекунды на каждую сборку; если цена важна, правила приложения
лучше вынести в отдельный пакет-провайдер —
[провайдер только с правилами](./authoring-providers.md#провайдер-только-с-правилами).
