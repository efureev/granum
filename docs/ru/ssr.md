# Серверный рендер

> 🇬🇧 English version: [`../en/ssr.md`](../en/ssr.md).

granum не требует от SSR ничего особенного, но две вещи нужно решить осознанно:
откуда берётся CSS и кто выбирает режим. Обе решаются один раз и дальше не
мешают. Рабочий пример целиком — стенд [`apps/app-ssr`](../../apps/app-ssr).

## CSS: собирать по модулям не нужно

Весь CSS приложения — один ассет с пятью каскадными слоями, на который ссылается
шаблон. Поэтому обычная для SSR работа «собрать стили отрендеренных модулей и
вписать их в ответ» здесь не нужна: собирать нечего, ссылка уже в шаблоне.

Серверный вход `virtual:granum.css` не импортирует вовсе — это делает только
клиентский:

```ts
// src/entry-client.ts
import 'virtual:granum.css'
```

```ts
// src/entry-server.ts — стилей не импортирует
import { renderToString } from '@vue/server-renderer'
```

Так же решается вопрос о `--ssrManifest`: он нужен тогда, когда CSS разрезан по
маршрутам и каждому ответу требуется свой набор ссылок. У granum набор один на
всё приложение, поэтому и манифест ни к чему.

## Режим выбирает сервер

Тема выбрана на сборке, и значения всех её режимов уже лежат в CSS. Переключение
режима — это пара в атрибуте корня: `data-theme="slate-dark"`. Значения пар знает
только сборка, и в рантайм они приезжают манифестом:

```ts
import manifest from 'virtual:granum/themes'

manifest.modes
// [{ name: 'light', colorScheme: 'light', value: 'slate-light' },
//  { name: 'dark',  colorScheme: 'dark',  value: 'slate-dark' }]
```

Если режим выбирает браузер после гидрации, первый кадр всегда чужой: сервер отдал
один режим, клиент немедленно переключил на другой. Поэтому решение принимается на
сервере и записывается в открывающий тег документа — парой, и для режима по
умолчанию тоже: клиент прочитает её обратно.

```ts
// src/entry-server.ts
import { modeFromCookie, themeRootAttributes } from '@feugene/granum/runtime'

const mode = modeFromCookie(manifest, request.headers.cookie)?.name ?? manifest.defaultMode
const attrs = themeRootAttributes(manifest, mode)   // { 'data-theme': 'slate-dark' }
```

Выбор пользователя доезжает до сервера cookie: на клиенте его пишет
`createCookieStorage()`, сервер читает `modeFromCookie`. Имя, которого нет среди
режимов сборки, `modeFromCookie` не возвращает: блоков CSS под него не
эмитировано. Отдавайте режим по умолчанию, а не страницу без токенов.

## Без сервера: скрипт до первого кадра

Статическому приложению пару ставит инлайн-скрипт в `<head>` — раньше, чем браузер
нарисует первый кадр. Скрипт пары, уже выставленной сервером, не трогает; иначе
берёт режим из cookie (если задано её имя), из `localStorage`, по системной схеме
и, наконец, режим по умолчанию.

```ts
import { createThemeScript } from '@feugene/granum/runtime'

const script = createThemeScript({ manifest, nonce, cookie: 'granum-theme' })
// '<script nonce="…">(function(){…})()</script>' — в <head> шаблона
```

Плагин вставляет его сам при `granum(config, { themeScript: true })` — первым в
`<head>` HTML-точки входа. SSR-приложение вставляет строку само или обходится
парой, которую пишет сервер.

## Клиент читает режим, а не выбирает заново

```ts
// src/entry-client.ts
const controller = createThemeController(manifest, { storage: createCookieStorage() })
```

Контроллер, поднятый поверх уже выставленной пары, узнаёт по ней режим и корень
не трогает, поэтому первый клиентский кадр совпадает с серверным. Хранит он имя
режима, а не пару: смена темы на сборке не сбрасывает выбор пользователя. Читать
выбор из `localStorage` в обход сервера не нужно: если сервер отдал один режим,
а клиент переключит на другой, получится ровно та вспышка, от которой SSR и уходят.

## Разметка не зависит от источника режима

Контроллер — вещь браузерная. Чтобы разметка получилась одинаковой на обеих
сторонах, компоненты не должны его знать: им нужно имя активного режима и способ
его сменить.

```ts
export interface ActiveMode {
  readonly name: string
  readonly list: readonly string[]
  readonly set: (name: string) => void
}
```

На сервере `set` — пустая операция, в браузере он зовёт `setMode` контроллера.
Приложение прокидывает эту пару через свой механизм внедрения зависимостей, и
разметка получается одинаковой с обеих сторон.

## Рантайм в Node

Точка входа `@feugene/granum/runtime` объявлена браузерной: без `node:`-импортов
и без внешних зависимостей. «Браузерная» не значит «падает на сервере»: без DOM
контроллер конструируется, отвечает на вопросы о режимах и текущем режиме и просто
не применяет его. Это позволяет пользоваться им на сервере для проверки имени режима.

## granum на сервере

Пакеты из `node_modules` серверная сборка Vite оставляет внешними: сервер грузит
их `dist` в рантайме. Провайдер, собранный `granumProvider`, granum при этом не
импортирует — хелперы контракта встроены в его `dist`, — так что granum может
оставаться в `devDependencies`, и деплой с `--omit=dev` работает. Исключение —
серверный код самого приложения: если он импортирует `@feugene/granum/runtime`
(контроллер режимов, как в стенде), granum нужен в `dependencies` или в
`ssr.noExternal`. Провайдер, собранный granum до 2.0, тянет
`@feugene/granum/contract` в рантайм — его достаточно пересобрать.

## Что проверять у себя

Стенд `apps/app-ssr` проверяет это скриптом, который импортирует собранный
серверный бандл и рендерит им. Минимальный набор для своего приложения:

1. один и тот же запрос даёт ту же разметку;
2. пара режима видна на корне, и чтение с корня возвращает тот же режим;
3. старт контроллера не меняет корень, а переключение меняет;
4. неизвестное имя режима откатывается к режиму по умолчанию, cookie выбирает режим;
5. ассет CSS один, и шаблон на него ссылается;
6. провайдеры из `node_modules` грузятся без granum, как после `--omit=dev`.
