# `app-ssr`

Стенд серверного рендера. Проверяет то, что нельзя проверить обычной сборкой:
как granum ведёт себя, когда первый кадр страницы собирает Node, а не браузер.

```bash
yarn workspace @granum-apps/app-ssr build     # dist/client + dist/server
yarn workspace @granum-apps/app-ssr verify    # рендер и утверждения
yarn workspace @granum-apps/app-ssr dev       # http://localhost:5180/?mode=dark
```

## Что здесь показано

| Грань | Где видно |
|---|---|
| режим выбирает сервер — из `?mode=` или cookie — и пишет пару в корень документа | `src/entry-server.ts`, `src/theme.ts`, `rootTag` в результате рендера |
| клиент не выбирает режим заново: контроллер узнаёт пару | `src/entry-client.ts`, `createCookieStorage` |
| замыкание графа между пакетами | `XgQuick` тянет `XTest1` из другого провайдера |
| CSS компонента, инлайненный по манифесту | `.x-sp-test` в слое `components` |
| токены из данных темы `heavy` | `XhCard` |
| токены компонента для темы `heavy` из `themesDir` | `XTokenized` |
| обрезка токенов по разметке приложения | `pruneTokens: { mode: 'on' }` и класс `text-[var(--x-tokenized)]` |

Три провайдера в одной резолюции, тема `heavy` с двумя режимами в CSS, четыре
компонента в селекции — разнородность намеренная: смысл стенда в том, что
серверный рендер ничего из этого не меняет.

## Почему режим решается на сервере

Значения всех режимов темы уже в CSS. Переключение режима — пара в атрибуте
корня: `data-theme="heavy-dark"`. Значения пар знает только сборка, и в рантайм
они приезжают манифестом `virtual:granum/themes`.

Если режим выбирает браузер после гидрации, первый кадр всегда чужой: сервер
отдал один режим, клиент переключил на другой. Поэтому режим выбирается на
сервере, пишется парой в открывающий тег — и для режима по умолчанию тоже — и
читается клиентом обратно. Контроллер поднимается поверх выставленной пары и
корень не трогает; выбор пользователя он кладёт в cookie, и следующий ответ
сервер рендерит уже в нём.

## Почему серверу не нужен CSS

Весь CSS приложения — один ассет с пятью слоями, на который ссылается шаблон.
Собирать стили по отрендеренным модулям, как это делают при code splitting CSS,
не нужно: собирать нечего. Серверный бандл `virtual:granum.css` не импортирует
вовсе — это делает только клиентский вход.

## Что проверяет `verify`

Скрипт [`scripts/verify-ssr.mjs`](../../scripts/verify-ssr.mjs) импортирует
собранный серверный бандл и рендерит им, то есть утверждает про наблюдаемый
результат, а не про текст исходников:

- `@feugene/granum/runtime` работает в Node без DOM;
- режим из `?mode=` и из cookie попадает на корень парой, и клиент прочитал бы
  из неё тот же режим;
- контроллер, поднятый поверх выставленной пары, корень не меняет, а
  переключение меняет;
- повторный рендер того же URL даёт ту же разметку;
- неизвестное имя режима откатывается к режиму по умолчанию, а не отдаёт
  страницу без токенов;
- ассет CSS ровно один, порядок слоёв тот же, что у обычной сборки;
- селекция, обрезка и диагностика совпадают с обычной сборкой;
- провайдеры из `node_modules` грузятся без granum, как после `--omit=dev`.

Проверка фальсифицируема: если `readActiveMode` начнёт возвращать режим по
умолчанию вместо прочитанного, падает чтение режима у ответов `dark` и
`cookie`; если контроллер перестанет узнавать выставленную пару, у тех же
ответов падает «старт контроллера изменил корень».
