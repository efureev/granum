# `app-ssr`

Стенд серверного рендера. Проверяет то, что нельзя проверить обычной сборкой:
как granum ведёт себя, когда первый кадр страницы собирает Node, а не браузер.

```bash
yarn workspace @granum-apps/app-ssr build     # dist/client + dist/server
yarn workspace @granum-apps/app-ssr verify    # рендер и утверждения
yarn workspace @granum-apps/app-ssr dev       # http://localhost:5180/?theme=dark
```

## Что здесь показано

| Грань | Где видно |
|---|---|
| тему выбирает сервер и пишет в корень документа | `src/entry-server.ts`, `rootTag` в результате рендера |
| клиент не выбирает тему заново, а читает применённую | `src/entry-client.ts`, `readActiveTheme` |
| замыкание графа между пакетами | `XgQuick` тянет `XTest1` из другого провайдера |
| CSS компонента, инлайненный по манифесту | `.x-sp-test` в слое `components` |
| токены темы из CSS-файлов провайдера | `XhCard` |
| токены темы, объявленные структурно | `XTokenized` |
| обрезка токенов по разметке приложения | `pruneTokens: { mode: 'on' }` и класс `text-[var(--x-tokenized)]` |

Три провайдера в одной резолюции, две темы в CSS, четыре компонента в селекции —
разнородность намеренная: смысл стенда в том, что серверный рендер ничего из
этого не меняет.

## Почему тема решается на сервере

Токены всех тем уже в CSS. Переключение темы — это приведение DOM в состояние,
при котором нужный блок начинает совпадать: атрибут, класс или ничего, если тема
эмитирована под `:root`. Знание о том, какой селектор у какой темы, есть только у
сборки, и в рантайм оно приезжает манифестом `virtual:granum/themes`.

Если тему выбирает браузер после гидрации, первый кадр всегда чужой: сервер
отдал одну тему, клиент переключил на другую. Поэтому тема выбирается на сервере,
пишется в открывающий тег и читается клиентом обратно. Контроллер поднимается
поверх уже применённого состояния и корень не трогает.

Тема с активацией `root` не пишет на корень ничего, и это не «нет темы», а
полноценное состояние: её токены под `:root`, она активна, пока не активирована
другая. Стенд проверяет обе ветки.

## Почему серверу не нужен CSS

Весь CSS приложения — один ассет с пятью слоями, на который ссылается шаблон.
Собирать стили по отрендеренным модулям, как это делают при code splitting CSS,
не нужно: собирать нечего. Серверный бандл `virtual:granum.css` не импортирует
вовсе — это делает только клиентский вход.

## Что проверяет `verify`

Скрипт [`scripts/verify-ssr.mjs`](../../scripts/verify-ssr.mjs) импортирует
собранный серверный бандл и рендерит им, то есть утверждает про наблюдаемый
результат, а не про текст исходников:

- `@feugene/granum/runtime` работает в Node без DOM (INV-THM-9);
- активная тема видна в разметке, и клиент прочитал бы из неё ту же тему
  (INV-THM-7);
- контроллер, поднятый поверх применённой темы, корень не меняет, а переключение
  меняет (INV-THM-8);
- повторный рендер того же URL даёт ту же разметку;
- неизвестное имя темы откатывается к теме по умолчанию, а не отдаёт страницу без
  токенов;
- ассет CSS ровно один, порядок слоёв тот же, что у обычной сборки;
- селекция, обрезка и диагностика совпадают с обычной сборкой.

Проверка фальсифицируема, это проверялось руками: если `readActiveTheme` начнёт
возвращать тему по умолчанию вместо прочитанной, падают четыре утверждения,
включая «старт контроллера изменил корень».
